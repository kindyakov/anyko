# MVP: автоматизация подготовки заявления о банкротстве физического лица

Дата обновления: 5 ноября 2026 года.

## 1. Цель и границы продукта

Веб-приложение для юриста или небольшой команды, которое помогает собрать заявление о банкротстве физического лица из документов клиента.

Юрист загружает документы, система извлекает сведения и показывает их для проверки. После подтверждения данных приложение собирает заявление в Word по одному заранее подготовленному шаблону.

Основной результат работы системы — проверенные данные дела с привязкой к источникам. Заявление является документом, сформированным из этих данных. ИИ извлекает факты, а текст и структура заявления задаются утверждённым шаблоном.

В MVP входят PDF, DOCX и фотографии или сканы документов. Основные примеры: паспорт, ИНН, СНИЛС, выписки БКИ, кредитные договоры, справки о задолженности, доходах, семье и имуществе.

## 2. Принятые решения

| Область | Решение |
| --- | --- |
| Основной язык | TypeScript |
| Среда выполнения | Bun для API, веб-приложения Next.js и отдельного фонового обработчика |
| Фронтенд | Next.js + React: страницы, формы и отображение состояния |
| Серверный API | Elysia + Bun: доступ к делам, операции с данными и запуск задач |
| Архитектура | Модульный монолит в одном репозитории; отдельные процессы frontend, API и worker; MinerU как отдельный сервис |
| Парсер и OCR | MinerU, размещённый в собственном контуре |
| Извлечение фактов | Внешняя LLM через OpenAI-совместимый API |
| Выбор провайдера и модели | Переключение в настройках администратора без изменения бизнес-логики и перезапуска приложения |
| Word | Один заранее подготовленный и размеченный шаблон DOCX |
| Генерация заявления | Программная сборка через docxtemplater и PizZip |

| Инженерная основа | Bun workspace, общие конфигурации, обязательные проверки и независимое продуктовое/инженерное review |

MinerU выбран для MVP. Сравнение нескольких OCR-продуктов не является отдельным этапом разработки. На примерах документов проверяются качество выбранного решения и подходящий режим его работы.

## 3. Пользовательский сценарий

1. Юрист создаёт дело и загружает документы клиента.
2. Приложение сохраняет файлы и запускает фоновую обработку.
3. Юрист видит состояние обработки каждого файла и сообщения об ошибках.
4. Система формирует карточку дела: сведения о должнике, семье, кредиторах, обязательствах, имуществе и счетах.
5. Юрист проверяет извлечённые сведения, открывает источники, исправляет значения и разрешает противоречия.
6. Приложение собирает заявление по подготовленному шаблону и позволяет скачать DOCX.
7. При добавлении новых документов система предлагает изменения в данных дела, сохраняя ранее подтверждённые сведения и ручные исправления.

Обработка продолжается после закрытия вкладки. При возвращении в дело пользователь видит сохранённое состояние и результаты.

## 4. Архитектура

Бизнес-логика находится в одном репозитории и разделяется на модули: дела, файлы, обработка, извлечение фактов, проверка и генерация документов. Принятое разделение компонентов описано в [архитектуре](docs/architecture.md).

Папки, владение данными, правила для агентов, тесты и выпуск определены в [инженерной основе](docs/engineering/README.md). [Направления развития](docs/roadmap.md) учитывают дополнительные шаблоны, профили обработки, отдельную админку, SaaS, оплату и агентский слой; их реализация не включается автоматически в MVP.

| Компонент | Ответственность |
| --- | --- |
| Фронтенд Next.js + React | Экраны входа, список дел, загрузка файлов, карточка дела, формы проверки и скачивание результата через API |
| API Elysia + Bun | Проверка аутентификации и прав доступа, операции с делами и документами, сохранение правок, настройки LLM и постановка задач |
| Worker на Bun | Управление этапами обработки, вызовы MinerU и LLM, сопоставление фактов и сборка Word |
| Общие TypeScript-модули | Схемы Zod и бизнес-правила для API и worker, независимые от HTTP-фреймворка |
| Модуль интеграции с LLM | Единый интерфейс OpenAI-совместимого API, выбор подключения, запрос структурированных данных и проверка ответа |
| Сервис MinerU | Разбор документов, OCR, извлечение текста, таблиц и структуры |
| PostgreSQL | Дела, сведения и их источники, подтверждения, история изменений, состояние обработки |
| BullMQ и Redis | Очередь фоновых задач, управление выполнением и повторными попытками |
| S3-совместимое хранилище | Исходные файлы, промежуточные результаты, шаблон и сформированные заявления |

Основной поток:

```text
Загрузка документов через фронтенд Next.js
        ↓
API Elysia + Bun → сохранение файлов и постановка задач в BullMQ
        ↓
Worker на Bun → извлечение текста / сервис MinerU
        ↓
Текст, страницы, блоки и таблицы
        ↓
OpenAI-совместимый API → выбранная LLM → факты по схеме дела → программные проверки
        ↓
Проверка и подтверждение юристом в Next.js → сохранение через Elysia API
        ↓
Отдельный worker → сборка DOCX по одному подготовленному шаблону
```

Next.js отвечает за фронтенд и рендеринг страниц. Бизнес-операции выполняются через Elysia API: их не дублируем в Route Handlers и Server Actions Next.js. Проверки доступа выполняются в API, независимо от интерфейса. Worker запускается отдельным процессом и получает задачи через BullMQ; длительные OCR, обращения к LLM и сборка Word не выполняются внутри пользовательского HTTP-запроса.

Сервис MinerU вызывается worker через внутренний API. Python и зависимости распознавания изолированы в этом сервисе. Работа с делами, пользовательские действия и правила формирования заявления остаются на TypeScript/Bun.

Фронтенд, Elysia API и worker можно первоначально разместить на одном сервере как отдельные процессы или контейнеры. Для браузера используется один домен: страницы обслуживает Next.js, маршруты `/api` направляются в Elysia. MinerU запускается отдельно и при необходимости переносится на машину с GPU. Требования к оборудованию определяются по выбранному режиму обработки и замерам на документах MVP.

## 6. Обработка документов и извлечение данных

### 6.1. Чтение и распознавание

Для DOCX и PDF с пригодным текстовым слоем используется прямое извлечение содержимого без обязательного OCR. MinerU применяется для сканов, фотографий и документов, которым требуется восстановление структуры и таблиц.

Способ обработки выбирается с учётом отдельных страниц: один PDF может содержать текстовые страницы и сканы. Наличие текстового слоя не считается гарантией его качества или корректного извлечения таблиц.

Результат приводится к внутреннему формату: документ, страницы, текстовые блоки и таблицы, а также координаты областей там, где их предоставляет выбранный режим MinerU. Сохраняются исходный результат и версия обработчика. Если координат нет, остаётся ссылка на файл, страницу и текстовый фрагмент.

Результаты сохраняются для повторного использования. Изменение карточки дела или повторная сборка Word не требуют нового OCR. Большие документы обрабатываются частями с сохранением контекста таблиц и связей между страницами.

### 6.2. Извлечение фактов

После разбора документов LLM извлекает сведения в заданную схему. Структура ответа проверяется через Zod; корректная структура не считается доказательством правильности значений.

MinerU отвечает за чтение документов. Отдельный этап извлечения определяет смысл сведений: кому принадлежат данные, к какому обязательству относится сумма, что она означает и на какую дату указана.

LLM не придумывает недостающие сведения и не пишет заявление свободным текстом. Ненайденные значения сохраняются как неизвестные и показываются юристу.

### 6.3. Подключение LLM и смена моделей

Для MVP используется внешняя LLM через OpenAI-совместимый API. Приложение работает с единым модулем интеграции и не привязывает бизнес-логику к конкретной модели или провайдеру.

Администратор настраивает подключения и выбирает активного провайдера и модель без изменения кода и перезапуска приложения. Подключение содержит адрес API (baseURL), API-ключ, идентификатор модели, режим структурированного ответа и ограничения запросов. Ключ хранится только на сервере и не передаётся в клиентское приложение при использовании модели.

При запуске задачи фиксируются выбранное подключение, модель и параметры обработки. Переключение настроек действует на новые задачи; уже запущенные продолжаются с зафиксированными настройками. Автоматический переход к другому провайдеру при ошибке по умолчанию отключён.

Все модели возвращают данные в единую схему дела. При поддержке используется структурированный ответ по JSON Schema; иначе запрашивается JSON с обязательной проверкой через Zod. Совместимость подключения и необходимые возможности проверяются перед его использованием. Некорректные ответы повторно запрашиваются ограниченное число раз, после чего задача получает понятный статус ошибки.

Для результата сохраняются провайдер, модель, версии инструкции и схемы, результат проверки и расход токенов, если API его сообщает. Ссылки на источники сопоставляются с существующими страницами и блоками документа.

Стартовая модель выбирается по точности извлечения на документах MVP, скорости и стоимости. Конкретная модель не является архитектурной зависимостью и может быть заменена через настройки.

Локально размещённая LLM — возможность дальнейшего развития. Если сервер локальной модели предоставляет необходимый OpenAI-совместимый API, его можно подключить через тот же модуль. Развёртывание локальной LLM не входит в обязательный объём MVP.

### 6.4. Сопоставление и проверки

Код проверяет форматы, рассчитывает суммы и выявляет возможные дубли обязательств. Денежные значения обрабатываются с точной десятичной арифметикой либо в целых копейках; неизвестная сумма не заменяется нулём.

Один кредит может встречаться в договоре, выписке БКИ и справке о задолженности. Система сопоставляет такие сведения с учётом кредитора, реквизитов договора, вида суммы и даты. Неоднозначные совпадения и противоречия передаются юристу. Правило «всегда взять самое свежее значение» не используется как универсальное.

## 7. Данные дела и проверка юристом

| Раздел | Содержание |
| --- | --- |
| Должник | ФИО, дата и место рождения, паспорт, ИНН, СНИЛС, адрес и контакты |
| Семья | Семейное положение, супруг, дети и подтверждающие документы |
| Кредиторы и обязательства | Реквизиты кредитора, договор, состав задолженности, дата суммы и источники |
| Имущество и счета | Недвижимость, транспорт, банковские счета и связанные сведения |
| Доходы | Сведения о доходах и периодах, необходимые подготовленному шаблону |
| Параметры заявления | Суд, СРО и другие данные, предусмотренные шаблоном |
| Источники и история | Документы, страницы, фрагменты, извлечённые варианты и изменения юриста |

Извлечённые факты и подтверждённое состояние дела хранятся отдельно. Повторная обработка предлагает обновления, но не перезаписывает ручные исправления автоматически.

Для значений различаются состояния: не найдено, извлечено, требует проверки, противоречие и подтверждено. Отсутствие сведений об имуществе, семье или обязательствах не означает подтверждённого отсутствия этих объектов.

Уже в MVP доступна форма редактирования с переходом к источнику. Полноценный синхронизированный интерфейс из двух панелей можно добавить позже. Ручное заполнение предусмотрено для данных, которых нет в документах.

## 8. Один подготовленный шаблон Word

В MVP используется один утверждённый, заранее подготовленный и размеченный DOCX. Загрузка произвольных шаблонов пользователем, редактор шаблонов и автоматическая разметка не входят в первую версию.

Шаблон задаёт формулировки, оформление, условные разделы и повторяющиеся таблицы. Приложение подставляет подтверждённые данные и вычисленные значения через docxtemplater и PizZip.

Каждое сформированное заявление связано с версией шаблона и снимком данных дела. Исправления в карточке позволяют собрать новую версию документа без повторного распознавания исходников.

Итоговая сборка требует проверки обязательных сведений и разрешения конфликтов. При необходимости допускается отдельно обозначенный черновик с заметными заглушками для пропусков; он не считается проверенным заявлением.

Оформление проверяется на длинных ФИО и адресах, разных количествах кредиторов и многостраничных таблицах. Шаблонизация не гарантирует неизменное число страниц при любых данных.

## 9. Надёжность и работа с файлами

Состояние каждого этапа сохраняется. Повторные попытки обработки не создают дубли фактов или документов. Ошибка одного файла не уничтожает результаты остальных; пользователь видит причину и может повторить обработку.

Доступ к делам и файлам ограничен авторизованными пользователями. Исходники хранятся в закрытом хранилище, содержимое клиентских документов не включается в обычные технические логи. Для MVP предусматриваются резервное копирование и удаление дела вместе с его файлами и производными результатами.

До пилота действует закрытый допуск пользователей в рабочую область; самостоятельная регистрация команд не требуется. Принадлежность дел, файлов и запусков рабочей области проверяется с первой реализации, даже при одной пилотной команде. Намерение фоновой обработки сохраняется в PostgreSQL атомарно с outbox; очередь доставляет задания, а повторные попытки и удаление проверяются по актуальному состоянию данных.

MinerU размещается в собственном контуре, а LLM в MVP вызывается через внешний API. Провайдер получает распознанный текст и таблицы, которые могут содержать персональные данные. До обработки реальных дел определяется список разрешённых подключений и допустимость передачи им клиентских сведений. API-ключи и содержимое документов не включаются в обычные технические логи. Локальный OCR сам по себе не означает, что весь процесс остаётся локальным.

## 10. Крупные задачи разработки

| Задача | Результат |
| --- | --- |
| 1. Согласовать данные дела и привязать готовый шаблон | Определены обязательные поля, источники, ручное заполнение и правила формирования разделов заявления |
| 2. Собрать фронтенд, API и worker | Работают Next.js, Elysia + Bun, отдельный worker на Bun, сохранение данных, файловое хранилище и очередь; проверен сквозной сценарий |
| 3. Подключить MinerU | Документы превращаются в текст и таблицы с привязкой к источникам; известны качество, время и потребление ресурсов на примерах MVP |
| 4. Реализовать извлечение и сопоставление фактов | Работают OpenAI-совместимый API и настройки провайдера и модели; формируется карточка дела, обнаруживаются пропуски, возможные дубли и противоречия |
| 5. Сделать проверку и сборку Word | Юрист подтверждает данные и получает заявление по подготовленному шаблону |
| 6. Провести пилот и подготовить рабочее размещение | Проверены полный сценарий, восстановление после ошибок, оформление документов и фактическое сокращение ручной работы |

## 11. Критерии готовности MVP

- Юрист проходит путь от загрузки документов до скачивания заявления в одном приложении.
- Фронтенд Next.js работает через Elysia API; длительные задачи выполняет отдельный worker на Bun и продолжает их после закрытия вкладки.
- Для извлечённых сведений можно открыть источник; неизвестные значения и конфликты видимы.
- Повторная обработка сохраняет ручные исправления и не создаёт дубли обязательств.
- Провайдер и модель переключаются через настройки без изменения кода; новые задачи используют выбранное подключение, а запущенные сохраняют свои параметры.
- Закрытие вкладки не прерывает обработку; ошибки файлов можно исправить и повторить задачу.
- Word собирается из подтверждённых данных по одному шаблону; оформление проверено на представительных делах.
- Проверены границы доступа рабочих областей, восстановление очереди и отсутствие публикации устаревшего результата после отмены/удаления.
- Выполнены применимые инженерные проверки и отдельные Product/Code review по [правилам качества](docs/engineering/quality.md); резервное восстановление проверено до работы с реальными делами.
- На пилоте измерены точность важных полей, пропуски строк таблиц, время обработки, ресурсы и время исправлений юристом.

## 12. Что остаётся определить и что отложено

До пилота нужно выбрать стартового API-провайдера и модель для извлечения фактов, режим и версию MinerU, оборудование, размещение данных и требования к качеству на примерах. Условия лицензирования выбранной версии MinerU учитываются при подготовке размещения. Выбор парсера и OCR, внешний API для LLM и возможность смены провайдера и модели уже зафиксированы.

За пределами MVP: развёртывание локальной LLM, произвольные пользовательские шаблоны, их автоматическая разметка, биллинг, полноценная SaaS-модель для независимых организаций и специализированные парсеры всех БКИ. Подключение локальной модели через тот же API и обогащение реквизитов через DaData или другие внешние источники можно добавить после пилота.
