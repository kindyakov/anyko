# Web-приложение

Правила `apps/web`. Причины решений — [ADR 0004](../adr/0004-code-organization.md) и [ADR 0008](../adr/0008-web-application-architecture.md). Оформление, Base UI и Tailwind описаны в [apps/web/AGENTS.md](../../apps/web/AGENTS.md); общие правила типов и ошибок — в [code-rules.md](code-rules.md).

## Структура

```text
apps/web/src/
  proxy.ts                    оптимистичное перенаправление без cookie сессии
  app/
    layout.tsx  providers.tsx  globals.css  not-found.tsx  global-error.tsx
    (public)/sign-in/         вход
    (workspace)/w/[workspace]/
      layout.tsx              сессия, проверка области, оболочка
      _shell/                 навигация и оболочка рабочей области
      works/                  список работ
      works/[id]/_screen/     экран работы: шаги и координация features
      recognition/            распознавание документов вне работы
      settings/connections/   подключения моделей; позже участники, тарифы
    api/[...path]/route.ts    прозрачный прокси к API
  features/<name>/
    index.ts                  публичный интерфейс
    ui/  api/  model/         появляются по необходимости
  lib/
    api/                      вызов endpoint-описаний, ошибки, query-клиент
    routes.ts                 функции адресов разделов
    server/                   server-only: конфигурация, сессия
```

Визуальные примитивы и токены находятся в `@anyko/ui`, фоновая графика бренда — в `@anyko/ui/brand`. До переноса пакета они временно лежат в `src/components`, и для них действуют те же правила.

## Уровни и импорты

| Откуда         | Разрешено                                                                               |
| -------------- | --------------------------------------------------------------------------------------- |
| `app/`         | `features/*/index.ts`, `@anyko/ui`, `lib/`, `@anyko/contracts`                          |
| `features/<a>` | свои файлы, `features/<b>/index.ts` без цикла, `@anyko/ui`, `lib/api`, contracts        |
| `@anyko/ui`    | React, Base UI, Tailwind, TanStack Form (в `form`); без contracts, `lib/api` и features |
| `lib/api`      | contracts и платформа браузера; без features                                            |
| `lib/server`   | только из серверных модулей: layouts, pages, route handlers, `proxy.ts`                 |

Contracts импортируются по ресурсам (`@anyko/contracts/works`, `/session`, `/common`); `@anyko/contracts/admin` пользовательскому web недоступен. Импорт `features/<b>/ui/...` из другой feature, `app/` из feature и feature из `@anyko/ui` — ошибки проверки границ. Новое ребро между features отражается в `index.ts` поставщика; цикл устраняется переносом координации в экран.

## Маршруты

- `page.tsx` и `layout.tsx` — серверные компоненты. Они читают `params`, вызывают `getSession()` при необходимости и рендерят features. Предметной логики и запросов к API за пределами сессии в них нет.
- Каждый раздел имеет `loading.tsx` и `error.tsx`; маршрут с параметром ресурса — `not-found.tsx`.
- Код, нужный только одному маршруту, лежит рядом в приватной папке `_screen/` или `_components/`. Если тот же код понадобился второму маршруту, это повод выделить feature, а не импортировать чужую приватную папку.
- Состояние, которым делятся ссылкой (фильтр, вкладка, открытый документ), хранится в адресе: search params или вложенный маршрут. Zustand — для локальных предпочтений интерфейса.
- Модальное окно с собственным адресом делается перехватывающим маршрутом; боковая панель с независимой загрузкой (агентская сессия) — параллельным маршрутом.
- Доступ проверяет API. `proxy.ts` и layout улучшают навигацию, но не считаются защитой.
- Все адреса рабочей области начинаются с `/w/[workspace]`. Layout сверяет область адреса с сессией; `/` ведёт в последнюю открытую область.
- Недоступное действие скрывается или блокируется через `useCan('<право>')` по правам из сессии. Это отображение, а не проверка доступа.

## Feature

Feature — один пользовательский сценарий в терминах [глоссария](../../GLOSSARY.md): `work-sources`, `fact-review`, `document-recognition`, `connections`. Техническое имя (`forms`, `tables`, `common`) не является feature.

- `index.ts` экспортирует компоненты, хуки и `queryOptions`, которые реально используются снаружи. Реэкспорт всего содержимого запрещён.
- Пока файлов немного, они лежат плоско. Подпапки `ui/` (компоненты), `api/` (ключи, запросы, команды, подписки), `model/` (чистые функции и типы отображения) появляются при разделении ответственностей.
- Компонент, который одновременно загружает данные, хранит черновик, выполняет команды и рисует несколько экранов, разделяется: данные — в хук `api/`, вычисления — в `model/`, части экрана — в отдельные компоненты.
- `'use client'` ставится на интерактивные компоненты, а не на весь экран.
- Feature не знает, на каком маршруте её показывают. Ссылки на другие разделы строятся функциями из `lib/routes.ts`.

## Данные

- Серверное состояние — только TanStack Query. Ключи задаёт фабрика своей feature: `workKeys.all`, `workKeys.detail(id)`. Строковые ключи в компонентах не пишутся.
- Запрос описывается `queryOptions` в `api/` и вызывает endpoint-описание из `@anyko/contracts` через `lib/api`. Пути и схемы в web вручную не пишутся. До перехода API на endpoint-описания действует `requestApi` со схемой ответа; ответ без схемы не используется.
- Команда — `useMutation`; после успеха она инвалидирует или обновляет затронутые ключи. Ручное копирование ответа в `useState` запрещено.
- SSE и опрос не хранят данные сами: событие инвалидирует ключ, опрос задаётся `refetchInterval`. Исключение — временный поток токенов агента: текст показывается по мере поступления в состоянии компонента, а после завершения или переподключения принятый ответ читается из API через инвалидацию.
- Команда, которая создаёт ресурс или начинает запуск, отправляет `Idempotency-Key`. Ключ создаётся на одно намеренное действие пользователя (отправку формы, клик) и повторно используется при повторе после сетевой ошибки; новый ключ на повтор не создаётся. `callApi` требует ключ для endpoint с признаком идемпотентности.
- Ключи включают рабочую область. Смена области или выход очищают кэш.
- 401 обрабатывается query-клиентом: кэш очищается, пользователь переходит на вход. Features не принимают `onUnauthorized`.
- Feature держит таблицу текстов для кодов ошибок своих endpoint с проверкой полноты (`satisfies Record<Code, string>`): новый код без текста — ошибка типов. Общие технические коды и итоговое сообщение строит `describeApiError` из `lib/api`.

## Формы

- Каждая форма строится на TanStack Form через `useAppForm` из `@anyko/ui/form`. Features не импортируют `@tanstack/react-form` напрямую; ручные `useState` на поля и собственная разводка ошибок не пишутся.
- Предметные правила формы (перенос правок на новую редакцию, вычисление конфликтов) — чистые функции в `model/` с unit-тестами; форма только принимает их результат через `reset`.
- Поля сведений строятся по каталогу полей, который API отдаёт вместе с пакетом документов. Web не перечисляет ключи полей профиля в коде.
- Ввод проверяется схемой из contracts для обратной связи; сервер проверяет его снова. Ошибки `invalid` с `fields` раскладываются по полям, тексты — из таблицы кодов feature.
- Несохранённый черновик живёт только в памяти формы и не попадает в localStorage, sessionStorage или Zustand с persist. Форма с несохранёнными правками предупреждает при уходе со страницы.
- Отправка — `useMutation` feature; форма не вызывает API сама.

## UI

Компоненты из `@anyko/ui` не знают о работах, документах и API. Если примитиву нужен предметный смысл, он остаётся в feature. Новый примитив сначала ищется среди Base UI и существующих компонентов.

## Тестирование

| Что проверяется                                   | Инструмент                                                          | Где           |
| ------------------------------------------------- | ------------------------------------------------------------------- | ------------- |
| Чистые функции `model/`, ключи, тексты ошибок     | `bun test`                                                          | рядом с кодом |
| Компоненты и хуки: формы, состояния, команды      | `bun test` + happy-dom + React Testing Library + user-event         | рядом с кодом |
| Маршруты, сессия, перенаправления, async RSC, SSE | Playwright, runner на Node, приложение через `bun --bun next start` | `tests/e2e`   |

- Web-тесты запускаются по маске файлов `src` с изоляцией файлов (`--isolate`), а не списком. Глобальный DOM регистрируется в preload web-пакета; серверные тесты его не получают.
- Компонент проверяется через роли и доступные названия, как его использует человек. Внутреннее состояние, имена классов и вызовы хуков не проверяются.
- Каждый тест создаёт свой `QueryClient`. Сеть подменяется на уровне `fetch` ответами, проходящими схемы contracts; модули features не мокируются.
- `next/navigation` и `next/link` подменяются общим помощником web-тестов, а не в каждом файле по-своему.
- Async Server Components не имитируются в unit-тестах: их поведение проверяет Playwright через тот же прокси и cookie, что и размещённое приложение.

Bun выбран для компонентных тестов осознанно: один runtime и runner для всего workspace и высокая скорость. Поддержка DOM в `bun test` в 2026 году быстро меняется, поэтому версия Bun закрепляется, а решение пересматривается при одном из условий:

- зависания или утечки состояния между файлами в CI, которые не устраняются закреплением версии и изоляцией, — web-тесты переходят на Vitest с jsdom на Node;
- нужен порог покрытия по ветвлениям, которого нет у `bun test`;
- фокус, всплывающие слои и pointer-события Base UI нельзя проверить в эмуляции — такие компоненты проверяются в Vitest Browser Mode или Playwright component tests точечно, остальные остаются на Bun.

## Как соблюдаются правила

Правило соблюдается гарантированно, только если его нарушение останавливает `verify:fast`, обязательную проверку PR. Поэтому каждое правило либо проверяется автоматически, либо относится к review. Проверки не должны требовать правки при каждой новой feature.

Автоматической проверкой становится правило, которое:

- выражает архитектурный инвариант, а не вкус;
- формулируется через соглашение о путях (`features/*/api/**`, `app/**`), а не через перечень конкретных features, файлов или имён;
- почти не даёт ложных срабатываний на правильном коде;
- в сообщении об ошибке говорит, как исправить нарушение.

Если новая feature, раздел или форма требуют дописать конфигурацию проверки, ошибка в проверке: её обобщают или возвращают в review. Конфигурации ESLint и dependency-cruiser не перечисляют имена features.

**Базовый набор.**

| Правило                                                                                         | Проверка                                                 |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Уровни, импорт чужой feature через `index.ts`, без циклов, `lib/server`, `contracts/admin`      | dependency-cruiser                                       |
| Клиент API вызывается только из `features/*/api` и `lib/api`                                    | dependency-cruiser                                       |
| Hooks, Next, доступность                                                                        | рекомендуемые наборы react-hooks, `@next/next`, jsx-a11y |
| Тесты через роли, без прямого доступа к DOM                                                     | рекомендуемый набор testing-library                      |
| Features не импортируют `@tanstack/react-form` и persist Zustand, не используют browser storage | `no-restricted-imports`, `no-restricted-globals`         |
| `Idempotency-Key`, полнота текстов ошибок                                                       | типы `callApi` и `satisfies`                             |

**Только review.** Имена по глоссарию, размер и ответственность компонента, выбор между адресом и Zustand, строковые query keys, `'use client'` на уровне экрана, чистота `model/`, польза тестов.

**Как набор растёт.** Если одно и то же нарушение из списка review повторяется во второй задаче, его переводят в автоматическую проверку. При этом проверка должна соответствовать критериям выше и сопровождаться контрольными примерами в `tests/architecture`: нарушение ловится, правильный код проходит. Проверку, которая часто ошибается или требует исключений, ослабляют или возвращают в review.

**Исключения.** Точечное отключение — `eslint-disable-next-line <правило> -- <причина>`; причина обязательна, review оценивает её. Временные исключения переходного периода перечисляются в конфигурации одним списком со ссылкой на задачу, которая их убирает. Постоянных исключений для отдельных файлов нет.

## Рецепты

**Новый раздел.** Папка в `app/(workspace)/w/[workspace]/<section>/` с `page.tsx`, `loading.tsx`, `error.tsx`; пункт навигации в `_shell`; функция адреса в `lib/routes.ts`.

**Новая feature.** `features/<name>/index.ts` и минимальный набор файлов; запросы в `api/` с фабрикой ключей; тест поведения; правило архитектуры не требует изменений, если зависимости идут вниз.

**Новый запрос к API.** Endpoint-описание в `@anyko/contracts`, ключ в фабрике feature, `queryOptions` в `api/`, использование через `useQuery`/`useSuspenseQuery`.

**Новая команда.** `useMutation` в `api/` feature-владельца, инвалидация затронутых ключей, тексты для кодов ошибок endpoint в таблице feature.

**Новый общий компонент.** Только если он нужен двум features и не содержит предметного смысла; добавляется в `@anyko/ui` вместе с проверкой доступности.

## Перед отчётом

- Импорты соответствуют таблице уровней; `bun run boundaries` и lint без ошибок.
- Нет новых строковых query keys, `useEffect` для загрузки данных и пропсов `onUnauthorized`.
- Экран проверен на настольной и узкой ширине, с клавиатуры, в состояниях загрузки, ошибки и пустого списка.
- Тесты добавлены по [правилам review тестов](test-review.md).
