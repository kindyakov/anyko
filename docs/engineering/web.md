# Web-приложение

Правила `apps/web`. Причины решений — [ADR 0004](../adr/0004-code-organization.md) и [ADR 0008](../adr/0008-web-application-architecture.md). Оформление, Base UI и Tailwind описаны в [apps/web/AGENTS.md](../../apps/web/AGENTS.md); общие правила типов и ошибок — в [code-rules.md](code-rules.md).

## Структура

```text
apps/web/src/
  proxy.ts                    оптимистичное перенаправление без cookie сессии
  app/
    layout.tsx  providers.tsx  globals.css  not-found.tsx  global-error.tsx
    (public)/sign-in/         вход
    (workspace)/w/[workspace]/
      layout.tsx              сессия, проверка области, оболочка
      _shell/                 навигация и оболочка рабочей области
      works/                  список работ
      works/[id]/_screen/     экран работы: шаги и координация features
      recognition/            распознавание документов вне работы
      settings/connections/   подключения моделей; позже участники, тарифы
    api/[...path]/route.ts    прозрачный прокси к API
  features/<name>/
    index.ts                  публичный интерфейс
    ui/  api/  model/         появляются по необходимости
  lib/
    api/                      вызов endpoint-описаний, ошибки, query-клиент
    routes.ts                 функции адресов разделов
    server/                   server-only: конфигурация, сессия
```

Визуальные примитивы и токены находятся в `@anyko/ui`, фоновая графика бренда — в `@anyko/ui/brand`, формы — в `@anyko/ui/form`.

## Уровни и импорты

| Откуда         | Разрешено                                                                         |
| -------------- | --------------------------------------------------------------------------------- |
| `app/`         | `features/*/index.ts`, `@anyko/ui`, `lib/`, `@anyko/contracts`                    |
| `features/<a>` | свои файлы, `features/<b>/index.ts` без цикла, `@anyko/ui`, `lib/api`, contracts  |
| `@anyko/ui`    | React, Base UI, Tailwind, TanStack Form (в `form`); без contracts, `apps/` и Next |
| `lib/api`      | contracts и платформа браузера; без features                                      |
| `lib/server`   | только из серверных модулей: layouts, pages, route handlers, `proxy.ts`           |

Contracts импортируются по ресурсам (`@anyko/contracts/works`, `/session`, `/common`) и по месту объявления символа; корневого экспорта у пакета нет (неразрешимый импорт отклоняет `workspace-imports-must-resolve`), `@anyko/contracts/admin` пользовательскому web недоступен. Импорт `features/<b>/ui/...` из другой feature, `app/` из feature, импорт `apps/`, Next или contracts из `@anyko/ui` и графики `brand` из корня `@anyko/ui` или `form` — ошибки проверки границ. Новое ребро между features отражается в `index.ts` поставщика; цикл устраняется переносом координации в экран.

## Маршруты

- `page.tsx` и `layout.tsx` — серверные компоненты. Они читают `params`, вызывают `getSession()` при необходимости и рендерят features. Предметной логики и запросов к API за пределами сессии в них нет.
- Каждый раздел имеет `loading.tsx` и `error.tsx`; маршрут с параметром ресурса — `not-found.tsx`.
- Код, нужный только одному маршруту, лежит рядом в приватной папке `_screen/` или `_components/`. Если тот же код понадобился второму маршруту, это повод выделить feature, а не импортировать чужую приватную папку.
- Состояние, которым делятся ссылкой (фильтр, вкладка, открытый документ), хранится в адресе: search params или вложенный маршрут. Zustand — для локальных предпочтений интерфейса.
- Модальное окно с собственным адресом делается перехватывающим маршрутом; боковая панель с независимой загрузкой (агентская сессия) — параллельным маршрутом.
- Доступ проверяет API. `proxy.ts` и layout улучшают навигацию, но не считаются защитой.
- Все адреса рабочей области начинаются с `/w/[workspace]`. Layout сверяет, что область адреса есть среди участий сессии (иначе 404). `/` ведёт в последнюю открытую область, если пользователь в ней участвует, иначе в первую из участий (`pickWorkspace`); без участий — на `/no-workspace`.
- Участие текущей области даёт `useMembership()`, право — `useCan('<право>')`; оба читают сессию из кэша. Недоступное действие скрывается или блокируется через `useCan` по правам из сессии. Это отображение, а не проверка доступа.

## Feature

Feature — один пользовательский сценарий в терминах [глоссария](../../GLOSSARY.md): `work-sources`, `fact-review`, `document-recognition`, `connections`. Техническое имя (`forms`, `tables`, `common`) не является feature.

- `index.ts` экспортирует компоненты, хуки и `queryOptions`, которые реально используются снаружи. Реэкспорт всего содержимого запрещён.
- В корне feature находятся только обязательный `index.ts` и необходимые папки `ui/`, `api/`, `model/`; пустые папки не создаются. Тест лежит рядом с проверяемым файлом, помощник теста — рядом с потребителями.
- Классификация по зависимостям: `ui/` содержит компоненты, хуки формы и поведения, контексты, Zustand и локальные иконки; `api/` — ключи, queryOptions, команды, подписки и хуки сети или query cache; `model/` — чистые функции, предметные и отображаемые типы, схемы форм, константы и тексты ошибок. Типы ответов выводятся из contracts, пропсы остаются в компоненте.
- Когда UI растёт, группируйте подкомпоненты и хуки по части экрана (`ui/preview/`, `ui/fields/`), без собственного index.ts. В каждой папке UI не более 10 файлов без тестов, в файле UI — не более 300 значимых строк без пустых строк и комментариев. Если у части отдельный сценарий и нужны собственные api и model, review решает о выделении feature. Папки hooks, types, utils, components и lib внутри feature не используются.
- Компонент, который одновременно загружает данные, хранит черновик, выполняет команды и рисует несколько экранов, разделяется: данные — в хук `api/`, вычисления — в `model/`, части экрана — в отдельные компоненты.
- `'use client'` ставится на интерактивные компоненты, а не на весь экран.
- Feature не знает, на каком маршруте её показывают. Ссылки на другие разделы строятся функциями из `lib/routes.ts`.

## Данные

- Серверное состояние — только TanStack Query. Ключи задаёт фабрика своей feature: `workKeys.all`, `workKeys.detail(id)`. Строковые ключи в компонентах не пишутся.
- Запрос описывается `queryOptions` в `api/` и вызывает endpoint-описание из `@anyko/contracts` через `callApi(endpoint, { params, query, body, idempotencyKey, signal, timeoutMs })` из `lib/api/call.ts`. Путь, параметры, тело и ключ собирает описание; тип входа выводится из его схем (`z.input`), результат — из схемы ответа (`z.output`), ответ проверяется ею же. `callApi` принимает только JSON-описания. Пути и схемы в web вручную не пишутся. `requestApi` — внутренний транспорт `lib/api`: features и app его не импортируют.
- При добавлении HTTP-метода в contracts экспортируйте его в прокси web `app/api/[...path]/route.ts`. Тест `lib/api/route.test.ts` сверяет поддержку методов.
- Файлы и поток событий не разбираются `callApi`: `endpointUrl(endpoint, { params, query })` даёт адрес той же версии API для ссылки на скачивание и `EventSource`.
- Команда — `useMutation`; после успеха она инвалидирует или обновляет затронутые ключи. Ручное копирование ответа в `useState` запрещено.
- SSE и опрос не хранят данные сами: событие инвалидирует ключ, опрос задаётся `refetchInterval`. Исключение — временный поток токенов агента: текст показывается по мере поступления в состоянии компонента, а после завершения или переподключения принятый ответ читается из API через инвалидацию.
- Команда, которая создаёт ресурс или начинает запуск, отправляет `Idempotency-Key`. Ключ действия ведёт `useIdempotencyKey()` из `lib/api/idempotency`: `take()` в обработчике намеренного действия (клик, отправка формы) отдаёт текущий ключ или создаёт новый, и он передаётся в переменных `useMutation`. `settle(error)` после исхода сбрасывает ключ при успехе и при определённом ответе сервера (ApiError со статусом, включая отказ `IDEMPOTENCY_CONFLICT`). При неизвестном исходе (сетевая ошибка, таймаут, обрыв, ошибка без статуса) ключ сохраняется: повтор того же действия передаёт тот же ключ, следующее действие после успеха или ответа — новый. Загрузка каждого файла получает свой ключ при выборе файлов: повтор загрузки означает новый выбор. `callApi` требует ключ на уровне типов для endpoint с режимом `key` и проверяет его в рантайме (UUID); для остальных режимов ключ не передаётся.
- Ключи включают рабочую область. Смена области или выход очищают кэш.
- 401 обрабатывается query-клиентом: кэш очищается, пользователь переходит на вход. Features не принимают `onUnauthorized`.
- Feature держит таблицу текстов для кодов ошибок своих endpoint с проверкой полноты (`satisfies Record<Code, string>`): новый код без текста — ошибка типов. Общие технические коды и итоговое сообщение строит `describeApiError` из `lib/api`.

## Формы

- Каждая форма строится на TanStack Form через `useAppForm` из `@anyko/ui/form`. Features не импортируют `@tanstack/react-form` напрямую: состояние формы читается через `useFormSelector` из того же модуля. Ручные `useState` на поля и собственная разводка ошибок не пишутся.
- Предметные правила формы (перенос правок на новую редакцию, вычисление конфликтов) — чистые функции в `model/` с unit-тестами; форма только принимает их результат. Перенос сведений (`fact-review/model/rebase.ts`): `base` — серверные значения, от которых начаты правки, `mine` — форма, `theirs` — новая редакция. Форма получает серверные значения через `reset`, затем `setFieldValue` только для полей, которые отличаются от них; конфликтные поля остаются с правкой пользователя, и сохранение недоступно до решения по каждому.
- Поля сведений строятся по каталогу полей, который API отдаёт вместе с пакетом документов. Web не перечисляет ключи полей профиля в коде.
- Ввод проверяется локальными схемами feature для обратной связи: тексты по-русски, ограничения повторяют contracts; сервер проверяет его снова. Ошибка поля показывается после потери фокуса или отправки. Ошибки `invalid` с `fields` раскладывает `applyServerErrors` (`lib/api/form-errors`): к полям с тем же именем, остальное — в общую ошибку формы; тексты — из таблицы кодов feature.
- Несохранённый черновик живёт только в памяти формы и не попадает в localStorage, sessionStorage или Zustand с persist. Форма с несохранёнными правками предупреждает при закрытии или перезагрузке вкладки (`useUnsavedChangesWarning`); переходы внутри приложения хук не перехватывает.
- Отправка — `useMutation` feature; форма не вызывает API сама.

## UI

Компоненты из `@anyko/ui` не знают о работах, документах и API. Если примитиву нужен предметный смысл, он остаётся в feature. Новый примитив сначала ищется среди Base UI и существующих компонентов.

## Тестирование

| Что проверяется                                   | Инструмент                                                          | Где           |
| ------------------------------------------------- | ------------------------------------------------------------------- | ------------- |
| Чистые функции `model/`, ключи, тексты ошибок     | `bun test`                                                          | рядом с кодом |
| Компоненты и хуки: формы, состояния, команды      | `bun test` + happy-dom + React Testing Library + user-event         | рядом с кодом |
| Маршруты, сессия, перенаправления, async RSC, SSE | Playwright, runner на Node, приложение через `bun --bun next start` | `tests/e2e`   |

- Web-тесты запускаются по маске файлов `src` с изоляцией файлов (`--isolate`), а не списком. Тесты `src/lib` запускаются без DOM, тесты `src/features` и `src/app` — с happy-dom через preload `test/setup.ts`.
- Компонент проверяется через роли и доступные названия, как его использует человек. Внутреннее состояние, имена классов и вызовы хуков не проверяются.
- Каждый тест создаёт свой `QueryClient`. Сеть подменяется на уровне `fetch` ответами, проходящими схемы contracts; модули features не мокируются.
- `next/navigation` и `next/link` подменяются общим помощником web-тестов, а не в каждом файле по-своему.
- Async Server Components не имитируются в unit-тестах: их поведение проверяет Playwright через тот же прокси и cookie, что и размещённое приложение.

Bun выбран для компонентных тестов осознанно: один runtime и runner для всего workspace и высокая скорость. Поддержка DOM в `bun test` в 2026 году быстро меняется, поэтому версия Bun закрепляется, а решение пересматривается при одном из условий:

- зависания или утечки состояния между файлами в CI, которые не устраняются закреплением версии и изоляцией, — web-тесты переходят на Vitest с jsdom на Node;
- нужен порог покрытия по ветвлениям, которого нет у `bun test`;
- фокус, всплывающие слои и pointer-события Base UI нельзя проверить в эмуляции — такие компоненты проверяются в Vitest Browser Mode или Playwright component tests точечно, остальные остаются на Bun.

## Как соблюдаются правила

Правило соблюдается гарантированно, только если его нарушение останавливает `verify:fast`, обязательную проверку PR. Как проектировать проверку, вести известные нарушения и отключения, когда переводить правило из review в автоматику — общие правила [quality.md](quality.md#как-проектировать-проверку-правила). Ниже — их применение к web. Конфигурации ESLint и dependency-cruiser формулируются через пути (`features/*/api/**`, `app/**`) и не перечисляют имена features: новая feature проходит проверки без их правки.

**Базовый набор.**

| Правило                                                                                                          | Проверка                                                   |
| ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Раскладка корня feature и максимум 10 файлов в каждой папке UI                                                   | архитектурный тест                                         |
| UI-файлы до 300 значимых строк, кроме списка известных нарушений                                                 | ESLint max-lines                                           |
| Уровни, импорт чужой feature через `index.ts`, без циклов, `lib/server`, `contracts/admin`                       | dependency-cruiser                                         |
| Features и app вызывают API только через `callApi`/`endpointUrl`; `client.ts` (requestApi) — только из `lib/api` | dependency-cruiser (`web-api-transport-only-in-lib`)       |
| Hooks, Next, доступность                                                                                         | рекомендуемые наборы react-hooks, `@next/next`, jsx-a11y-x |
| Тесты через роли, без прямого доступа к DOM                                                                      | рекомендуемый набор testing-library                        |
| Features не импортируют `@tanstack/react-form` и persist Zustand, не используют browser storage                  | `no-restricted-imports`, `no-restricted-globals`           |
| `Idempotency-Key`, полнота текстов ошибок                                                                        | типы `callApi` и `satisfies`                               |

**Только review.** Имена по глоссарию, ответственность компонента, выбор между адресом и Zustand, строковые query keys, `'use client'` на уровне экрана, чистота `model/`, польза тестов.

## Рецепты

**Новый раздел.** Папка в `app/(workspace)/w/[workspace]/<section>/` с `page.tsx`, `loading.tsx`, `error.tsx`; пункт навигации в `_shell`; функция адреса в `lib/routes.ts`.

**Новая feature.** `features/<name>/index.ts` и необходимые папки `ui/`, `api/`, `model/`; запросы в `api/` с фабрикой ключей; тест поведения; правило архитектуры не требует изменений, если зависимости идут вниз.

**Новый запрос к API.** Endpoint-описание в `@anyko/contracts`, ключ в фабрике feature, `queryOptions` в `api/`, использование через `useQuery`/`useSuspenseQuery`.

**Новая команда.** `useMutation` в `api/` feature-владельца, инвалидация затронутых ключей, тексты для кодов ошибок endpoint в таблице feature.

**Новая форма.** В компоненте feature: `const form = useAppForm({ defaultValues, onSubmit })`; `onSubmit` вызывает `useMutation` через `mutateAsync` и в `catch` передаёт ошибку в `applyServerErrors(formApi, error, texts)`. Поля — `<form.AppField name="…" validators={{ onChange: schema }}>` с `field.TextField` или `field.RadioGroupField`; разметка — `<FormRoot form={form}>` с `form.SubmitButton` внутри. Общая ошибка — `FormErrorNotice`. Если форма меняет сохранённые данные, вызовите `useUnsavedChangesWarning(useFormSelector(form.store, (s) => s.isDirty))` и после успеха `formApi.reset(значения)`. Тесты: отправка, клиентская проверка, серверная ошибка по `fields`, фокус на первом ошибочном поле.

**Новый шаг экрана работы.** Feature шага (`features/<шаг>/`) с `index.ts` и компонентом в `ui/`; команды, которые меняют работу, — в `api/` шага. Шаг подключается в `app/(workspace)/w/[workspace]/works/[id]/_screen/work-screen.tsx`: новый `Tabs.Panel` и, если шаг виден в степпере, ключ в `StepKey` и `journeySteps`; правила перехода между шагами — в `stepOf` и `workStage` (`features/works/model/journey.ts`). Шаг не импортирует другой шаг: общее для нескольких шагов переносится в `features/works`, координация остаётся в экране.

**Новый общий компонент.** Только если он нужен двум features и не содержит предметного смысла; добавляется в `@anyko/ui` вместе с проверкой доступности.

## Перед отчётом

- Импорты соответствуют таблице уровней; `bun run boundaries` и lint без ошибок.
- Нет новых строковых query keys, `useEffect` для загрузки данных и пропсов `onUnauthorized`.
- Экран проверен на настольной и узкой ширине, с клавиатуры, в состояниях загрузки, ошибки и пустого списка.
- Тесты добавлены по [правилам review тестов](test-review.md).
