# Размещение и эксплуатация

Подготовленные manifest, образы и ограниченное чтение журналов описаны в
[инструкции Dokploy](deployment.md). Фактическая приёмка сервера выполняется
отдельно от локальных проверок.

## Начальная топология

Docker Compose: отдельные образы/процессы `web`, `api`, `worker`; PostgreSQL, Redis, закрытый S3-compatible backend и MinerU как инфраструктурные зависимости. MinerU может находиться на отдельной GPU-машине с закрытым сетевым доступом. Один внешний домен: страницы → web, `/api` → API. Worker, БД и очередь не публикуются в интернет.

Сборка каждого приложения использует workspace и общий lockfile; образ содержит только нужные runtime-зависимости. Версии Bun, базовых образов и зависимостей закрепляются, образы маркируются commit/digest. Один проверенный образ продвигается между средами без пересборки. Секреты и адреса окружения подаются при размещении; публичная build-time конфигурация Next отдельно проверяется, чтобы продвижение образа не меняло смысл API-origin.

Мигратор — один release job из того же выпуска, не действие каждой реплики API. Prisma-команда выбирается под закреплённую версию и записывается в manifest; документация не предполагает, что CLI разных major одинаков. [Документация миграций Prisma](https://www.prisma.io/docs/orm/migrations/applying-a-migration).

Среды: локальная разработка с синтетическими данными, CI с изолированными зависимостями, staging для выпуска, production для реальных дел. У них разные секреты, хранилища и базы; тесты никогда не выбирают production по умолчанию. Изменения infrastructure/config проходят review вместе с кодом.

## Порядок выпуска

1. Собрать и проверить неизменяемые образы. Зафиксировать совместимые версии API, worker, схемы БД, job envelopes, процессоров и шаблонов.
2. Проверить backup/restore-процедуру для изменения, затрагивающего сохранённые данные. Применить расширяющую миграцию одним job. Миграция `202611180019_recognition_search` использует PostgreSQL 18 с расширением `pg_trgm`. Роль migrator должна иметь возможность создать расширение в целевой базе, если оно ещё отсутствует.
3. Выпустить worker, умеющий читать старые и новые payload, затем включить новый producer/API. Если одновременно поддерживать версии нельзя, приостановить постановку и безопасно завершить/мигрировать старые задания.
4. Выпустить frontend и выполнить release smoke через внешний proxy: вход, загрузка, запуск, статус, результат и проверка доступа.
5. Backfill выполняется повторяемой ограниченной задачей с прогрессом. Удаление старых колонок/версий происходит отдельным последующим выпуском после завершения совместимости.

Откат кода возможен только к версии, совместимой с уже применённой схемой и payload. Destructive rollback БД не выполняется автоматически. Ошибочная обработка не исправляется переписыванием старых результатов: новый run сохраняет происхождение. Обновление версии профиля учитывает незавершённые runs, которые были закреплены за старой реализацией: либо обе версии доступны, либо очередь этой версии предварительно дренируется.

Миграция `202611180035_idempotency_resource_reference` меняет кодировку сохранённых
ответов. Остановите старый API и дождитесь завершения его запросов до миграции.
Открывайте трафик после запуска API из выпуска с новой схемой.

## Процесс и наблюдаемость

API имеет liveness и readiness, ограниченные timeouts, размеры загрузок и rate limits. Readiness проверяет необходимую БД и конфигурацию; временная недоступность Redis не должна скрывать успешно сохранённый outbox, но выводит обработку в явно деградировавшее состояние. Ошибка внешнего LLM не превращает все HTTP endpoints в «нездоровые».

Worker публикует heartbeat и состояние consumer/dispatcher, перестаёт брать новые задания при остановке и завершает работу в ограниченный срок. Незавершённая попытка восстанавливается по lease, а поздний результат защищён fencing token. Локальный флаг `running` не является распределённой блокировкой. [BullMQ graceful shutdown](https://docs.bullmq.io/guide/workers/graceful-shutdown).

Журналы структурированы; единые поля: service, release, request/run/attempt ID, workspace scope при необходимости, код ошибки и длительность. Тексты документов, provider bodies, cookies и ключи не логируются. Для диагностики содержимого используются отдельно разрешённые артефакты с ограничением доступа и сроком хранения.

Минимальные эксплуатационные сигналы: возраст старейшего outbox/ожидающего задания, отсутствие heartbeat, длительность этапов, retry/failure rate, ошибки провайдеров, расход страниц/токенов, рост S3/БД, статус очистки и backups. Численные SLO и лимиты задаются после замеров вертикального сценария и до пилота; их не выводят из рекламных benchmark.

## Восстановление и данные

Backup охватывает БД, файлы, версии шаблонов и доступ к ключам шифрования секретов. Восстановление проверяется на отдельной среде с чтением источника и готового DOCX, соответствием метаданных S3 и остановкой исходящих обработок до сверки. Факт создания backup не является проверкой restore. Целевые RPO/RTO и срок хранения согласуются перед обработкой реальных дел.

Восстановленная копия не должна повторно отправлять старые оплаченные запросы автоматически. Сначала сверяются outbox/runs и внешние неопределённые исходы, затем оператор разрешает возобновление. Retention и порядок удаления охватывают производные файлы, диагностические артефакты и backups. Восстановление старой копии учитывает удаления, совершённые после её создания.

## Рост без смены модели

Первое масштабирование — больше реплик stateless API и отдельных worker-пулов по нагрузке: parsing, extraction, generation. Это может быть один образ worker с разной конфигурацией очередей. Установлены лимиты общего провайдера, ресурсов MinerU и параллелизма рабочей области; бесконечное увеличение concurrency не является планом масштабирования. Для нескольких Next-реплик согласуется стратегия cache/revalidation, а пользовательские данные не попадают в общий публичный cache.

При появлении операторского интерфейса добавляется `apps/admin` с отдельным размещением и политикой сессий. API предоставляет отдельные administrative permissions/routes; отделение UI не считается само по себе защитой. По потребности появляется отдельный admin API, но предметные команды сохраняют владельцев.

Разделение БД/сервиса допускается после измерений нагрузки или требования изоляции. ADR фиксирует владельца данных, миграцию, доставку событий, совместимость, observability и процедуру отката. Kubernetes, service mesh и отдельная БД каждого модуля не являются обязательной подготовкой к этому переходу.

## Выкат заданий и очередей

Для физического удаления работ сначала примените аддитивную миграцию
`202611180018_work_deletion_and_listing` и обновите API и worker. Перед
открытием нового API убедитесь, что все его экземпляры используют актуальную
версию. Для очистки нужна очередь `maintenance`. Если удаление долго остаётся
незавершённым, проверьте доступ к хранилищу и барьеры записей `ProcessingIo`.
Квитанция подтверждает очистку в рабочей базе и хранилище. Старые резервные
копии обрабатываются по правилам восстановления выше.

`WORKER_QUEUES` — список `ocr,llm,render,maintenance` через запятую; по умолчанию выбраны все четыре. Пробелы по краям имён допустимы, дубликаты убираются, неизвестное или пустое имя останавливает запуск с ошибкой конфигурации. Например, один процесс с `WORKER_QUEUES=ocr`, второй с `llm`, третий с `render,maintenance` используют один образ и отдельные пулы нагрузки. Масштабирование требует прежних лимитов OCR/LLM, БД и ресурсов области.

Техническая очередь `QUEUE_NAME` (`anyko-diagnostic`) запускается всегда, в том числе в пустом режиме без БД. `WORKER_QUEUES` не отключает диагностику, не меняет её CLI и readiness. Полный worker дополнительно включает readiness выбранных бизнес-очередей и PostgreSQL dispatcher.

### Выкат общего каталога (#44)

Перед миграцией `202611180020_shared_work_sources` остановите запись API. Дайте worker завершить запущенные удаления работ, затем остановите worker, снимите резервную копию и запустите один migrator. Миграция сохраняет идентификаторы исходных документов и запусков, меняет ключ связи и фиксирует готовую ревизию для существующих источников. Очереди сохраняются. Запустите API и worker из одного нового релиза. После проверки readiness проверьте открытие существующего источника, повтор OCR и добавление файла во вторую работу.

Для отката остановите API и worker, восстановите резервную копию и запустите прежнюю версию. После открытия записи оператор учитывает потерю изменений, сделанных позже резервной копии.

### Выкат #22 в окно обслуживания

Мигратор `202611170017_unified_processing` создаёт пустые `Run`, `RunStep`, `RunAttempt`, `RunOutbox` и `ProcessingIo`. Старая история, попытки, ожидающие доставки и барьеры записи удаляются в одной транзакции. Документы, работы, факты, файлы генерации, артефакты и история сессии остаются в своих таблицах. Старые OCR-результаты теряют ссылку запуска. Видимый документ можно распознать заново. Для нового анализа нужно повторно запустить его в работе.

1. Перед окном сохранить неизменяемые образы API и worker версии части 1. В Dokploy закрыть входящие записи, остановить приложения API и worker и дождаться завершения работы и запросов к S3/MinerU. В Compose остановить `api` и `worker` соответствующего проекта (`docker compose stop api worker`). Сервисы PostgreSQL и Redis оставить запущенными.
2. Убедиться, что записи `DocumentIo` и `WorkIo` разобраны. Запрос `SELECT (SELECT count(*) FROM "DocumentIo") AS document_writers, (SELECT count(*) FROM "WorkIo") AS work_writers;` должен вернуть два нуля. Если есть записи, проверить исходы внешних операций и выполнить документированное операторское восстановление на сохранённом образе части 1. Миграция старые барьеры не переносит.
3. Снять полный резервный снимок PostgreSQL после остановки записей. Запустить единственный migrator нового выпуска на целевой БД. Транзакция использует `lock_timeout=5s` и `statement_timeout=10min`. Старые имена очередей `anyko-document-ocr` и `anyko-work-pipeline` можно очистить адресно после остановки всех прежних worker. Формат текущего envelope и имена `ocr`, `llm`, `render`, `maintenance` остаются прежними. Доставка с UUID удалённого запуска отклоняется при проверке области исполнения. Старый формат envelope больше не обслуживается.
4. В Dokploy запустить API и worker из одного нового релиза. Для Compose обновить образы приложений и запустить `docker compose up -d api worker`. Проверить `/health/ready` API/worker, пустую историю запусков перед открытием записи и целостность состояния. Например, `SELECT kind, status, count(*) FROM "Run" GROUP BY kind, status;` и `SELECT count(*) FROM "Run" WHERE status='running' AND ("attemptToken" IS NULL OR "leaseUntil" IS NULL);` (второй запрос должен вернуть `0`). Проверить чтение сохранённых документов и работ. Открыть запись и проверить один новый запуск и доставку outbox.

Откат: остановить новые API и worker, восстановить резервный снимок PostgreSQL перед миграцией и запустить сохранённые образы части 1. Сравнить количества истории, проверить readiness и только затем открыть запись. **Записи после открытия нового API будут потеряны при восстановлении снимка.** Откат после открытия записи требует решения оператора. Старые очереди нельзя считать резервной копией данных.

Maintenance использует фиксированные ключи scheduler (имя и версия) в очереди `maintenance`: несколько реплик не создают по независимому расписанию. Обработчики очистки идемпотентны; аренда BullMQ исключает нормальное одновременное исполнение одного срабатывания, но после потери аренды возможен повтор. На ограниченных worker без `maintenance` глобальная очистка не выполняется — нужен хотя бы один maintenance consumer.

E2E использует тот же экспорт `@anyko/worker/queues` с префиксом BullMQ `anyko-e2e`. Подготовка удаляет только ключи `anyko-e2e:*`; production и другие тестовые префиксы не затрагиваются. Общий E2E-стенд запускается отдельно от integration на Redis 16379.

## Удаление работ на пакетах БФЛ v1–v11

1. Сверить состав удаляемых тестовых работ и снять резервную копию базы. Остановить запись API, завершить или отменить текущие запуски и остановить worker. Сохранить доступ нового worker к тому же хранилищу.
2. Единственным migrator применить `202611260074_retire_bfl_packages`. Она скрывает старые работы, отменяет оставшиеся запуски и ставит работы в очередь штатной очистки. Пакет и ключи файлов сохраняются, пока на них ссылаются строки очистки.
3. Запустить worker нового выпуска с очередью `maintenance`. Проверить, что очистка завершена и запрос ниже возвращает пустой результат. При `work_deletion_retry` проверить хранилище и незавершённый I/O работы. После устранения причины очередной проход maintenance повторит очистку. Перезапуск worker сохраняет состояние.
4. Запустить API нового выпуска. В каталоге создания работ используется v14, существующие работы v12–v14 продолжают открываться. Исходные документы и распознавание остаются в каталоге.

```sql
SELECT version
FROM "DocumentPackageVersion"
WHERE "packageId" = 'bfl-bankruptcy'
  AND version IN (SELECT anyko_retired_bfl_package_versions());
```
