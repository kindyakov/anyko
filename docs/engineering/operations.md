# Размещение и эксплуатация

Подготовленные manifest, образы и ограниченное чтение журналов описаны в
[инструкции Dokploy](deployment.md). Фактическая приёмка сервера выполняется
отдельно от локальных проверок.

## Начальная топология

Docker Compose: отдельные образы/процессы `web`, `api`, `worker`; PostgreSQL, Redis, закрытый S3-compatible backend и MinerU как инфраструктурные зависимости. MinerU может находиться на отдельной GPU-машине с закрытым сетевым доступом. Один внешний домен: страницы → web, `/api` → API. Worker, БД и очередь не публикуются в интернет.

Сборка каждого приложения использует workspace и общий lockfile; образ содержит только нужные runtime-зависимости. Версии Bun, базовых образов и зависимостей закрепляются, образы маркируются commit/digest. Один проверенный образ продвигается между средами без пересборки. Секреты и адреса окружения подаются при размещении; публичная build-time конфигурация Next отдельно проверяется, чтобы продвижение образа не меняло смысл API-origin.

Мигратор — один release job из того же выпуска, не действие каждой реплики API. Prisma-команда выбирается под закреплённую версию и записывается в manifest; документация не предполагает, что CLI разных major одинаков. [Документация миграций Prisma](https://www.prisma.io/docs/orm/migrations/applying-a-migration).

Среды: локальная разработка с синтетическими данными, CI с изолированными зависимостями, staging для выпуска, production для реальных дел. У них разные секреты, хранилища и базы; тесты никогда не выбирают production по умолчанию. Изменения infrastructure/config проходят review вместе с кодом.

## Порядок выпуска

1. Собрать и проверить неизменяемые образы. Зафиксировать совместимые версии API, worker, схемы БД, job envelopes, процессоров и шаблонов.
2. Проверить backup/restore-процедуру для изменения, затрагивающего сохранённые данные. Применить расширяющую миграцию одним job.
3. Выпустить worker, умеющий читать старые и новые payload, затем включить новый producer/API. Если одновременно поддерживать версии нельзя, приостановить постановку и безопасно завершить/мигрировать старые задания.
4. Выпустить frontend и выполнить release smoke через внешний proxy: вход, загрузка, запуск, статус, результат и проверка доступа.
5. Backfill выполняется повторяемой ограниченной задачей с прогрессом. Удаление старых колонок/версий происходит отдельным последующим выпуском после завершения совместимости.

Откат кода возможен только к версии, совместимой с уже применённой схемой и payload. Destructive rollback БД не выполняется автоматически. Ошибочная обработка не исправляется переписыванием старых результатов: новый run сохраняет происхождение. Обновление версии профиля учитывает незавершённые runs, которые были закреплены за старой реализацией: либо обе версии доступны, либо очередь этой версии предварительно дренируется.

## Процесс и наблюдаемость

API имеет liveness и readiness, ограниченные timeouts, размеры загрузок и rate limits. Readiness проверяет необходимую БД и конфигурацию; временная недоступность Redis не должна скрывать успешно сохранённый outbox, но выводит обработку в явно деградировавшее состояние. Ошибка внешнего LLM не превращает все HTTP endpoints в «нездоровые».

Worker публикует heartbeat и состояние consumer/dispatcher, перестаёт брать новые задания при остановке и завершает работу в ограниченный срок. Незавершённая попытка восстанавливается по lease, а поздний результат защищён fencing token. Локальный флаг `running` не является распределённой блокировкой. [BullMQ graceful shutdown](https://docs.bullmq.io/guide/workers/graceful-shutdown).

Журналы структурированы; единые поля: service, release, request/run/attempt ID, workspace scope при необходимости, код ошибки и длительность. Тексты документов, provider bodies, cookies и ключи не логируются. Для диагностики содержимого используются отдельно разрешённые артефакты с ограничением доступа и сроком хранения.

Минимальные эксплуатационные сигналы: возраст старейшего outbox/ожидающего задания, отсутствие heartbeat, длительность этапов, retry/failure rate, ошибки провайдеров, расход страниц/токенов, рост S3/БД, статус очистки и backups. Численные SLO и лимиты задаются после замеров вертикального сценария и до пилота; их не выводят из рекламных benchmark.

## Восстановление и данные

Backup охватывает БД, файлы, версии шаблонов и доступ к ключам шифрования секретов. Восстановление проверяется на отдельной среде с чтением источника и готового DOCX, соответствием метаданных S3 и остановкой исходящих обработок до сверки. Факт создания backup не является проверкой restore. Целевые RPO/RTO и срок хранения согласуются перед обработкой реальных дел.

Восстановленная копия не должна повторно отправлять старые оплаченные запросы автоматически. Сначала сверяются outbox/runs и внешние неопределённые исходы, затем оператор разрешает возобновление. Retention и порядок удаления охватывают производные файлы, диагностические артефакты и backups. Восстановление старой копии учитывает удаления, совершённые после её создания.

## Рост без смены модели

Первое масштабирование — больше реплик stateless API и отдельных worker-пулов по нагрузке: parsing, extraction, generation. Это может быть один образ worker с разной конфигурацией очередей. Установлены лимиты общего провайдера, ресурсов MinerU и параллелизма рабочей области; бесконечное увеличение concurrency не является планом масштабирования. Для нескольких Next-реплик согласуется стратегия cache/revalidation, а пользовательские данные не попадают в общий публичный cache.

При появлении операторского интерфейса добавляется `apps/admin` с отдельным размещением и политикой сессий. API предоставляет отдельные administrative permissions/routes; отделение UI не считается само по себе защитой. По потребности появляется отдельный admin API, но предметные команды сохраняют владельцев.

Разделение БД/сервиса допускается после измерений нагрузки или требования изоляции. ADR фиксирует владельца данных, миграцию, доставку событий, совместимость, observability и процедуру отката. Kubernetes, service mesh и отдельная БД каждого модуля не являются обязательной подготовкой к этому переходу.
