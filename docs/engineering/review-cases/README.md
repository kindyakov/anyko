# Контрольные примеры для reviewer

Небольшое учебное упражнение проверяет, отличает ли reviewer полезный тест от теста реализации и ложного доказательства. Это не скрытый benchmark, не оценка всей модели и не часть автоматического CI. Примеры публичны; повторный прогон может измерять узнавание.

При изменении инструкций review или существенной смене reviewer-процедуры:

1. Передать отдельному reviewer со свежим контекстом только [cases.md](cases.md), задачу оценить тесты и действующие правила [test-review.md](../test-review.md). Ключ заранее не передавать.
2. На каждый ID получить `accept`, `reject` или `needs-context`, конкретное основание и недостающее доказательство. Здесь `accept` означает пригодность описанной проверки для заявленного scope, а не готовность feature к выпуску.
3. После ответа сравнить с [ключом](expected.md). Отдельно посчитать пропущенные дефекты и ложные отклонения допустимых примеров; разногласия разобрать, а не подгонять ключ под ответ.
4. Записать версию примеров, reviewer/дату, выводы по ID, затраты при наличии измерения и ограничения. Неизвестные стоимость/время так и обозначить.

Проверка импортов имеет исполняемые примеры в [архитектурных тестах](../../../tests/architecture/boundaries.test.ts). Этот набор дополняет их смысловыми случаями. Реальные пропуски пополняют набор после независимой проверки expected. Для объективного сравнения процедур потребуются новые отложенные примеры, которых нет в инструкциях; сейчас такого закрытого набора нет.

Контроль оценивается по подтверждённым дефектам, пропускам, ложным блокировкам и стоимости разбора. Его упрощают, если тот же риск воспроизводимо покрывает более дешёвый механизм или риск исчез. Отсутствие находок само по себе не является поводом убрать защиту доступа/денег/данных.

Первый учебный прогон: [результаты v1](results-2026-11-05.md). Это проверка понятности процедуры на примерах, а не сертификат качества модели.
