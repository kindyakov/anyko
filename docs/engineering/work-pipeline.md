# Работы, модели и заполнение документа

Требования: [Issue #2](https://github.com/kindyakov/anyko/issues/2) и последующее поручение о пакете из трёх документов; [ADR 0006](../adr/0006-document-packages.md) уточняет [ADR 0005](../adr/0005-template-works-and-agent-runtime.md). Пользователь выбирает пакет из 1..N шаблонов. Действующий пакет и версии его бланков перечислены в [README бланков](../../packages/backend/src/modules/templates/assets/README.md). Исходные заполненные DOCX обезличены; их оригиналы не являются runtime-зависимостью и не предназначены для публикации.

## Владельцы и исполнение

`works` владеет работой, связями с исходниками, редакцией и событиями. `documents` сохраняет исходники, результат MinerU и отдельные изображения в закрытом S3. `processing` владеет запусками, шагами, outbox, lease и версиями подключения. `facts` сопоставляет кандидаты и сохраняет ручные решения. `templates` предоставляет неизменяемый бланк; `generation` хранит снимок значений и собранные DOCX. `agents` использует Mastra и PostgreSQL-память в схеме `anyko_agents`.

Координация — процессы `workflows/work-*`, сборка и ресурсы — `runtime/works`. Серверный `@anyko/llm` не знает Prisma, пользователей, файлов и очереди: создаёт SDK-модель по явно переданным настройкам. Пакет запрещён для web/contracts/ui. Next-маршруты компонуют feature `works` через общий экран сессии.

Три процесса остаются прежними. Worker обслуживает очереди OCR и `anyko-work-pipeline`. Запуск и outbox фиксируются атомарно в PostgreSQL; Redis не хранит единственную копию намерения. Envelope содержит версию, scope и run ID. CAS по attempt token и lease защищает принятие результата; просроченный запуск и его outbox восстанавливаются одним SQL-оператором.

Этапы: распознавание исходников → описания вложенных изображений → извлечение по файлам → сопоставление → отдельная генерация DOCX. При `ANYKO_ANALYSIS_STEPWISE=true` worker заменяет извлечение и сопоставление пошаговой сессией [ADR 0013](../adr/0013-unified-work-agent-session.md). По умолчанию используется `false`, и worker выполняет извлечение и сопоставление отдельными этапами. Другие значения отклоняются при старте. Отдельные изображения расшифровывает vision-модель при распознавании. При анализе работы их сохранённая транскрипция поступает в извлечение как текст. Ошибка файла сохраняется, остальные обрабатываются. Успешные шаги извлечения повторно используются при неизменных входах и версии подключения. Сбой до сохранения успешного ответа может потребовать повторного платного вызова: exactly-once для провайдера не обещается.

## Агентский контекст и данные

Текст подаётся фрагментами до 64000 символов с перекрытием 2000. Каждый фрагмент целиком передаётся агенту извлечения. Доступные описания изображений передаются с первым фрагментом. Модель возвращает структурированные кандидаты за один шаг без инструментов чтения. Первый запрос использует опубликованный предел ответа модели. Для RouterAI с несколькими доступными поставщиками учитывается наименьший опубликованный предел. Для других совместимых подключений предел читается из карточки модели, если провайдер его публикует. Без опубликованного предела запрос использует 64000 токенов. При обрыве на лимите файл получает ошибку LLM_COMPLETION_LIMIT. Из завершённого ответа можно локально убрать обрамление JSON. Если структурированный ответ всё ещё непригоден, допускается один повтор с тем же лимитом и настройкой рассуждения. В каждой попытке доступен один транспортный повтор SDK. Извлечение, сопоставление и облачное OCR получают потоковые ответы. Запрос прерывается после 120 секунд без содержательных фрагментов. Текст, рассуждение и данные вызова инструмента сбрасывают таймер. SSE-комментарии, пустые фрагменты и метаданные таймер не сбрасывают. Ошибка тишины — LLM_STREAM_IDLE, при OCR — OCR_STREAM_IDLE. Ошибки показываются для конкретного файла. У запуска deadline 25 минут, lease 30 минут; параллелизм потребителя — один. История Mastra ограничена 12000 токенов, semantic/observational memory и автоматические заголовки выключены. Большой контекст разбивается; отсутствие данных остаётся неизвестным. Zod и точная цитата не доказывают истинность извлечения — сведения проверяет человек.

Фотографии и изображения DOCX дополнительно нормализуются процессором в JPEG; все кадры TIFF учитываются с лимитом 32. Оригинал сохраняется отдельно. Байты изображения передаются модели только в запросе, не дублируются в сообщениях Mastra. Vision возвращает читаемый текст с сохранением связей между значениями и добавляет визуальные детали, которые влияют на извлечение. Описания и кандидаты — версионированный JSON шага с путями исходных изображений. При несовпадении ревизии инструкции vision новый запуск обновляет описание и зависящее от него извлечение. Неподдержанная графика DOCX и превышение лимитов дают явную ошибку.

Ручные правки имеют приоритет; противоречащие значения остаются кандидатами, поле не выбирается произвольно. Сохранение требует актуальную редакцию. Генерация фиксирует значения, подтверждение и версию пакета; поздняя правка не меняет старый результат. Шаблон сохраняется в S3 под версией и checksum и проверяется перед сборкой через docxtemplater/PizZip. Строки обязательств сопоставляются по кредитору/должнику и основанию; конфликтующие значения сохраняются для проверки. Неизвестный состав (`null`) отличается от явно указанного отсутствия (`[]`). Просительная часть и приложения не наследуются из конкретного дела.

Извлечение и сопоставление используют одну схему кандидатов для запроса и проверки ответа. Банковский кандидат содержит одну строку из ячеек `column` и `value` с ключами поля. Явное отсутствие предпринимательских обязательств представляется пустым массивом `businessDebts` с цитатой. Реестровые колонки доступны серверному поиску. В цитате пробельные последовательности сравниваются как один пробел. При сравнении сохраняются буквы, цифры, знаки и исходный текст самой цитаты. Строку недвижимости могут подтверждать несколько цитат одного документа, если в них есть значение каждой заполненной ячейки. Более поздняя дата расчёта в справке по тому же договору блокирует автоматический выбор ранней суммы, даже если свежего кандидата нет. Если актуальную строку нельзя подтвердить, поле обязательств остаётся пустым для проверки юристом.

## HTTP, SSE и настройки

`/api/v1/document-packages`, `/api/v1/workspaces/:workspaceId/works`, `/api/v1/workspaces/:workspaceId/works/:id` дают каталог, список и снимок. Подмаршруты работы: `documents`, `analyze`, `fields`, `confirm`, `generate`, `generations/:id/files/:fileId`, `events`. Источники и предпросмотр документа работы доступны через проверяемые `/api/v1/workspaces/:workspaceId/works/:id/documents/:documentId/source`, `/result`, `/images/:index`.

Чат использует этот же `/events`. Worker каждые 250 мс публикует новые фрагменты текста ответа и рассуждения в Redis Stream работы. При ходе чата в очереди или в обработке API ждёт дельты через Redis XREAD BLOCK. Журнал работы читается по уведомлениям PostgreSQL и при восстановлении соединения. `chat-progress` содержит номер попытки и номер фрагмента. `Last-Event-ID` несёт курсоры PostgreSQL и Redis, поэтому переподключение дочитывает пропущенные фрагменты. Для перезагрузки `GET /messages` возвращает черновик с номером фрагмента, сохранённый примерно раз в 2,5 секунды при изменениях. При разрыве последовательности браузер сразу обновляет этот снимок. Если запись черновика ещё не завершилась, событие chat.checkpoint запускает следующее обновление. При ошибке публикации worker повторяет отправку того же фрагмента с прежним номером. Redis не блокирует сохранение снимка в PostgreSQL. API переподключается к Redis и проверяет, активен ли тот же ход, прежде чем продолжить передачу. Финальный ответ, рассуждение и состояние запуска сохраняются одной транзакцией. Записи Redis ограничены 512 фрагментами и живут 5 минут с последней записи. При удалении работы её сообщения удаляются по каскаду, а временный поток очищается при удалении производных данных. Пока Redis недоступен, очистка повторяется, а поток API пропускает только дельты активного хода.

Каталог полей принадлежит профилю БФЛ в backend и передаётся в составе пакета: ключ, подпись, тип, колонки и ограничения. Web строит редактор из ответа, а HTTP-контракт описывает формат, не перечисляя поля профиля. Сохранённые факты версии 1 читаются со значениями по умолчанию для отсутствовавших полей; проверка допустимых полей и колонок выполняется в backend до записи. Ошибки тела содержат `fields` с путями из строковых и числовых сегментов и стабильными кодами; тексты ошибок задаёт web.

Scope выдаёт `access` по области из адреса и участию (Membership); изменения проверяют origin. Чужой ID не даёт доступ к работе, событиям или скачиванию. `/api/v1/workspaces/:workspaceId/connections/llm` меняет только участник с правом `connections.manage` (owner). API не возвращает ключ; новый шифруется AES-256-GCM с workspace AAD. Запуск фиксирует revision подключения, смена модели применяется к новым запускам. Vision/extraction выбираются независимо, автоматического fallback между моделями нет.

Ревизия подключения хранит `visionDisableReasoning` и `extractionEnableReasoning`. При пропуске поля в `PATCH` сохраняется выбор для того же адреса API и модели. Для нового адреса или модели извлечение по умолчанию запрашивает высокий уровень. При `false` извлечение явно запрашивает средний уровень. OCR и описание вложенных изображений используют одну настройку. Для нового адреса API или vision-модели по умолчанию запрашивается отключение рассуждений. Если провайдер его не поддерживает, можно выбрать режим провайдера.

Снимок читает cursor перед данными: изменения могут прийти повторно, но не пропасть между снимком и подпиской. Записи журнала SSE несут тип изменения и курсор. Web перечитывает данные, сохраняя открытую форму. События снятия источника сбрасывают старые данные чата; удаление работы закрывает её поток и убирает карточку. `Last-Event-ID` проходит через Next proxy. Отзыв права закрывает поток в течение 15 секунд. Лимит — четыре потока на пользователя в рабочей области и 100 на API-процесс. Прокси должен пропускать поток без буферизации.

Пакет и состав шаблонов записаны в `DocumentPackageVersion`, `DocumentTemplateVersion`, `PackageDocument`. Работа закрепляет `packageVersion`. `WorkGeneration` фиксирует общий снимок, `WorkGenerationFile` хранит отдельные статусы, ключи и checksums. Состав связан внешними ключами, успешный файл не скрывается из-за ошибки другого. Ошибка storage с неизвестным исходом продолжает подниматься до durable I/O барьера. Исторические версии сохранены; техническая версия скрыта из каталога UI, но её создание через API оставлено для совместимости старых клиентов.

[Подготовка DOCX и предпросмотра](../../packages/backend/src/modules/templates/assets/README.md): исходные стили и структура сохраняются, служебные поля заменяют данные конкретного дела. В браузере три бланка переключаются вкладками и используют общие значения. Полное совпадение браузерной пагинации и Word не обещается.

## Полное удаление и восстановление

Журнал `WorkEvent` хранится до удаления работы и очищается каскадно. Миграция `202611210071_work_event_lock_order` берёт блокировку строки работы перед advisory lock курсора, чтобы публикация события не входила во взаимную блокировку с изменением этой же работы. При непрерывном ответе чат добавляет около 24 записей `chat.checkpoint` в минуту. У журнала пока нет очистки по возрасту. Сохранение черновика сериализовано отдельно от публикации дельт, поэтому ожидание блокировки PostgreSQL не останавливает Redis Stream.

Удаление исходника сразу скрывает зависимые сведения и скачивания. Cleanup ждёт durable DocumentIo/WorkIo барьеры, удаляет смешанные результаты работы, генерации и их S3-объекты, сообщения/сессии Mastra, затем снимает связь с исходником. После этого document cleanup завершает физическое удаление. Оставшиеся исходники можно обработать заново; ручные значения тоже очищаются, поскольку могли содержать удалённые сведения. UI предупреждает об этом до удаления.

Неопределённый исход S3 PUT оставляет `uncertain` барьер. После crash его нельзя снимать по возрасту. Оператор подтверждает остановку всех API/worker, завершение внешних записей и дренирование MinerU, затем запускает `bun run documents:recover-writes --applications-stopped --storage-requests-drained`. Команда восстанавливает также WorkIo; последующий worker очищает зарегистрированные ключи. Это не гарантия удаления у RouterAI/конечного провайдера или из резервных копий.

## Локальный запуск и доказательства

После `bun install --frozen-lockfile` и `bun run db:generate` примените миграции к локальной базе. В игнорируемом `.env`: `WORKS_ENABLED=true`, `DOCUMENTS_ENABLED=true`, приватный `LLM_CONFIG_ENCRYPTION_KEY` из 32 случайных байтов в hex. Режим один из двух: оба флага `true` (полный, нужны БД, S3, ключ и для worker MinerU с Redis) либо оба `false` (пустой, только проверка готовности). Смешанное сочетание завершает старт с кодом `CONFIG_MODE_MISMATCH` в журнале. Ключ одинаков у API и worker; его потеря делает существующие подключения нечитаемыми.

Подключение задаётся owner через интерфейс. Для начального RouterAI есть `bun --env-file=.env --env-file=.env.routerai.local run llm:provision`: отдельный игнорируемый файл содержит `ROUTERAI_API_KEY` и `ROUTERAI_BASE_URL`. Команда сохраняет существующие настройки. Модель по умолчанию `~deepseek/deepseek-v4-flash-latest`, альтернативный ID `minimax/minimax-m3.1-flash` задаётся в настройках.

`bun run dev` загружает конфигурацию и запускает приложения. Не используйте hostname другого проекта: `APP_ORIGIN`, `AUTH_BASE_URL` и фактический адрес страницы должны совпадать. Секретов нет во frontend env.

`bun run test:llm` проверяет готовый SDK на контролируемом HTTP-провайдере. `bun run test:works` — приоритет правок и конфликты. `bun run test:works:integration` требует отдельную `anyko_test` и тестовый Redis: настоящие БД/outbox/BullMQ и управляемый agent port. `bun run test:processor` проверяет stateless lifecycle и визуальный экспорт. CI не выполняет платные LLM-запросы. Browser и live extraction — отдельные уровни доказательств.

## Проверка визуального анализа

Визуальный анализ проверяет исходный текст завершённого ответа по JSON-схеме. При невалидном ответе файл получает ошибку, остальные исходники продолжают обрабатываться. Бюджет ответа vision задаётся переменной worker `ANYKO_VISION_MAX_OUTPUT_TOKENS`. По умолчанию используется 4800 токенов, допустимый диапазон от 1 до 16 384. Верхняя граница оставляет запас для плотных документов и ограничивает максимальный бюджет ответа. Для временных ошибок транспорта действует один повтор SDK. Для каждого запроса действует таймаут тишины.

## Постоянный контекст работы

`agents` владеет `WorkAgentSession` и `WorkAgentTurn`; [ADR 0007](../adr/0007-persistent-work-agent-session.md) описывает выбор отдельных Mastra threads для попыток. Логическая сессия создаётся вместе с новой работой; существующие работы получают её при анализе. Сессия и её версия сохраняются в PostgreSQL, каждый принятый turn содержит revision, run ID, зарегистрированный thread ID, событие `documents.analyzed` и версионированный контекст/выход. Неудачные и устаревшие ответы остаются только историей попыток и не становятся принятым контекстом.

После извлечения из файлов `continue-session` восстанавливает факты и последнее принятое состояние. Координатор через `@mastra/core`/Memory получает перечень источников и состояния полей. Инструменты читают актуальные поля и текст/описания разрешённых исходников фрагментами до 16000 символов, с проверкой текущей работы на каждом чтении. Переменная worker `ANYKO_RECONCILE_MAX_READS` задаёт предел инструментальных чтений (по умолчанию 24, от 1 до 256), а `ANYKO_RECONCILE_MAX_MODEL_CALLS` — предел модельных вызовов (по умолчанию 12, от 1 до 64). Каждый вызов модели использует таймаут тишины. Общий предел задаёт задание работы. Предел ответа общий для всех вызовов, он описан ниже в разделе пилота. Нет инструментов записи фактов и нет отдельного самописного agent loop.

Исходные кандидаты не подавляются моделью. Контекстные предложения имеют `origin=context`, проходят схемы и проверку точных цитат и отображаются отдельно. Сводка до 4000 символов не является доказательством. Пустые и противоречивые поля вычисляются из принятых фактов. Перед commit выполняется CAS-fence текущей попытки и проверка work/session revision. При ручной правке сопоставление пересобирается максимум один раз. При ошибке модельного этапа прежние кандидаты сохраняются; запуск становится partial, старая сводка остаётся явно устаревшей.

Кэш извлечения файлов сохраняется. Координатор запускается заново на каждом намеренном анализе, читает текущие факты и настройки; контекстный результат не кэшируется по одному document checksum. Смена провайдера не требует переноса его внутреннего reasoning state. Полная история принятых обращений сохраняется в БД, а в prompt отправляется ограниченное последнее состояние и актуальный канонический контекст. Для хода чата вход также включает последнее сообщение пользователя и недавние завершённые сообщения этой работы. Переменная worker `ANYKO_CHAT_MAX_MODEL_CALLS` ограничивает число модельных вызовов на ход. По умолчанию используется 8, допустимый диапазон от 1 до 64.

В пилоте ADR 0013 переменная worker `ANYKO_ANALYSIS_MAX_MODEL_CALLS` задаёт предел модельных вызовов на шаг. По умолчанию 32, допустимый диапазон от 1 до 64. Если последний вызов планирует продолжить работу инструментом, шаг получает ошибку `LLM_STEP_LIMIT`. История указывает ключ шага, контрольная точка сохраняет черновик, а сведения завершённых шагов участвуют в публикации результата.

Шаги анализа, сверка, чат и прежнее извлечение используют один расчёт бюджета. Модели передаётся опубликованный максимум токенов ответа по маршруту, при неизвестном максимуме — 64 000. Для входа учитываются предел промпта и контекстное окно маршрута с запасом под схемы и оценку токенов. Если резерв полного ответа не оставляет места для рабочего промпта, ограничение входа рассчитывается по самому окну. При отсутствии данных о маршруте история сжимается по резервному бюджету. В прежнем извлечении одиночный фрагмент источника передаётся целиком на проверку провайдеру. Порог опубликованного окна проверяет gateway до обращения за ответом модели, в том числе перед описанием изображений. Переменная worker `ANYKO_MIN_MODEL_CONTEXT_TOKENS` задаёт положительное целое число (по умолчанию 131072). Для RouterAI проверяется наименьшее опубликованное окно доступных маршрутов. Если оно ниже порога, этап получает `LLM_CONTEXT_TOO_SMALL` и предлагает выбрать в настройках модель с большим окном. При отсутствии опубликованного окна сохраняется резервный расчёт.

Переменные worker `ANYKO_ANALYSIS_MAX_READS` и `ANYKO_ANALYSIS_REVIEW_MAX_READS` задают бюджет чтений полей, источников и метаданных изображений. По умолчанию обычный шаг получает 24 чтения, итоговая сверка — 64. Для обоих настроек допустимы целые значения от 1 до 256. Счётчики чтений и модельных вызовов сверки сохраняются в контрольной точке.

Перед сверкой сервер вычисляет пустые автоматические поля с учётом черновика и решений юриста. Агент может предложить значение с цитатой либо записать причину пропуска. Заполненные поля защищены при каждом вызове. При попытке завершить сверку сервер возвращает непокрытые поля в ту же сессию. При исчерпании лимита или ошибке модели проверенные предложения сверки публикуются по общим правилам. История показывает код ошибки, ключи непокрытых полей и частичную сводку с уже записанными причинами.

API снимка работы возвращает `session` с ID, revision, context и updatedAt. На странице показаны сводка, поля для проверки и предупреждение об устаревании после правки. Чтение снимка защищено work lock, чтобы session и facts соответствовали одной редакции. Удаление исходника очищает session/turns и все Mastra threads после существующего durable I/O барьера.
