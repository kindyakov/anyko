# Данные, доступ и фоновые задания

## Владение и изоляция

Рабочая область — граница бизнес-данных с первой реализации. Один пользователь может иметь несколько участий; клиент юриста не является владельцем пространства. В MVP достаточно одной созданной оператором области и закрытого допуска пользователей. Самостоятельное подключение организаций, тарифы и оплата появляются позже.

Выбранный адаптер аутентификации — Better Auth на Elysia, с серверной сессией; его совместимость с закреплёнными Bun/Prisma версиями проверяется в первой вертикали. Password/session primitives не пишутся самостоятельно. Публичная регистрация закрыта, первичный доступ и восстановление учётной записи оформляются проверенным административным сценарием. Бизнес-роли и membership принадлежат модулю `access`, независимо от формы таблиц auth-библиотеки. Основание выбора: [официальная интеграция Elysia/Bun](https://better-auth.com/docs/integrations/elysia).

MVP-роли рабочей области: `owner` управляет доступом и настройками области, `member` работает с её делами. Отдельная роль `platform-operator` управляет платформенными подключениями и допуском команд; она не даёт неявного доступа к содержимому дел. Пользователь может одновременно иметь разные роли в разных областях. Настройки глобального LLM-подключения доступны оператору; будущие подключения команды получают явный scope рабочей области.

API получает workspace scope только после проверки сессии и участия. `workspaceId` из URL/тела не доказывает доступ. Серверный сценарий и repository получают обязательный доверенный scope; поиск только по resource ID без него не является публичным методом. Ответ на чужой ID не раскрывает данные или существование чужого дела.

У бизнес-таблиц есть явный `workspaceId`, tenant-scoped уникальности и составные внешние ключи там, где они защищают от ссылки в другую область. Глобальные identity/config/template записи помечаются как глобальные сознательно. Общая БД сама по себе не обеспечивает эту изоляцию: требуются ограничения и отрицательные интеграционные тесты.

S3-объект принадлежит записи конкретного владельца. Имя ключа или знание URL не заменяет авторизацию. Скачивание начинается с проверки доступа; выдаваемая подписанная ссылка ограничена сроком, что ограничивает скорость её отзыва. Worker получает доступ только к ресурсам разрешённого запуска. Секреты подключений зашифрованы, ключ шифрования отделён от БД и включён в план восстановления.

## Кто владеет данными

Ниже концептуальные группы, а не готовая SQL-схема. Точные колонки и индексы появляются вместе со сценарием и миграцией.

| Модуль | Данные и единственный владелец записи |
| --- | --- |
| `access` | пользователи/сессии через auth-адаптер, рабочие области, участия, роли |
| `cases` | карточка и lifecycle дела, запрос удаления |
| `documents` | исходные файлы и версии, разбор, страницы/блоки, source artifacts |
| `processing` | запуски, этапы, попытки, leases, outbox, разрешённые подключения и их версии, технический расход |
| `facts` | кандидаты и evidence-ссылки, решения юриста, конфликты, редакции подтверждённых сведений |
| `templates` | один утверждённый manifest и файл версии в MVP; постоянный каталог при расширении |
| `generation` | снимок входных сведений, ссылка и checksum шаблона, состояние и артефакт результата |

Схема и миграции физически едины в `database`. Изменение общей схемы требует review предметного владельца. Это не разрешение читать и менять любую таблицу из любого модуля. Соседний модуль запрашивает данные через публичный query/command. Read model для сложного экрана вводится явно с владельцем, scope и перечнем источников; случайный join в HTTP-handler не допускается.

Стабильные сущности, связи, доступ и lifecycle имеют типизированные колонки. JSON используется для версионированного содержимого extraction/snapshot, с runtime-проверкой и путём чтения прежних версий. Универсальная EAV-модель и один постоянно растущий `case.data` не заменяют предметную модель. В MVP case kind фиксирован как БФЛ; общие jobs не знают его обязательных полей.

## Транзакции и конкурентные правки

Один модуль обычно завершает команду своей транзакцией. Сценарий, который должен атомарно сохранить изменение и намерение обработки, использует узкий unit-of-work порт: он получает связанные с одной транзакцией публичные командные интерфейсы модулей, а не Prisma client. Реализация находится в runtime/persistence. Публикация в Redis, S3, OCR и LLM не происходит внутри длинной транзакции БД.

Команды внутри unit-of-work используют переданный транзакционный scope и не открывают независимые commit. Предметное изменение, запуск и outbox сохраняются одним commit. Повтор callback транзакции не повторяет внешние побочные эффекты.

Подтверждение фактов использует ожидаемую редакцию. При конкурентной правке возвращается конфликт, а не молчаливое последнее сохранение. Generation фиксирует согласованный снимок подтверждённых сведений, параметров дела и версии шаблона; позднейшие изменения создают новый результат. Результаты извлечения остаются предложениями и не заменяют ручные решения.

Даже единственный DOCX-шаблон хранится как неизменяемый durable asset по versioned key, а не только внутри текущего образа. Ссылка, checksum и совместимая schema/profile version закрепляются в генерации. Worker загружает именно эту версию; отсутствие файла или несовпадение checksum даёт явную ошибку, без перехода на latest. Версия удерживается, пока на неё ссылаются запуски/результаты в пределах политики хранения.

## Доставка и исполнение

1. API проверяет пользователя и команду. Idempotency key ограничен областью, видом команды и отпечатком входа; тот же ключ с иным входом отклоняется. Новый намеренный запуск получает новый ключ.
2. В одной транзакции сохраняются запуск/ожидаемый этап и outbox-запись. HTTP возвращает ID после commit, даже если Redis временно недоступен.
3. Dispatcher внутри worker арендует outbox-записи и отправляет ID в BullMQ. Повторная доставка допустима; состояние PostgreSQL определяет, нужно ли исполнять этап.
4. Исполнитель захватывает этап условным обновлением и получает attempt/fencing token. Payload имеет версию, run/step/workspace IDs и correlation ID; содержимое документов и ключи в Redis не копируются.
5. Worker загружает зафиксированные входы, проверяет scope, актуальность ресурса и разрешённость подключения, выполняет ограниченный по времени шаг.
6. Результат принимается атомарно, только если attempt token, lifecycle и ожидаемые версии ещё действительны. Уникальность `(run, stage, inputRevision)` защищает от второго принятого результата. Если шаг породил продолжение, следующая outbox-запись сохраняется в той же транзакции.
7. Reconciler повторно доставляет недоставленное, обнаруживает потерянные/просроченные leases и убирает осиротевшие артефакты. Несколько dispatcher/reconciler реплик используют блокировки или условные захваты, а не локальный флаг процесса.

PostgreSQL хранит различимые состояния ожидания, исполнения, retry, успеха, ошибки и отмены. Redis — механизм доставки, а не единственная история. Идемпотентность очереди не заменяет уникальности и проверки в БД. [BullMQ рекомендует идемпотентные задания](https://docs.bullmq.io/patterns/idempotent-jobs).

Payload является указателем, не источником полномочий. Worker сверяет workspace/run/step IDs с каноническим запуском в PostgreSQL и строит scope из сохранённой разрешённой операции. Неизвестная версия, несовпадение ID или отсутствующий запуск отклоняются без исполнения.

S3 не участвует в транзакции PostgreSQL: артефакт сначала пишется в уникальный ключ попытки; успешный commit публикует метаданные владельца. Непринятые или незавершённые объекты очищаются после безопасного периода с проверкой отсутствия владельца. Повторная попытка не перезаписывает ключ уже опубликованного результата.

## Снимки конфигурации и стоимость

При запуске фиксируются профиль/processor version, document versions, схема извлечения, prompt version, connection version, модель и параметры. Секрет хранится по ссылке на серверную версию, а не в payload. Обычное изменение активных настроек касается новых запусков. Отзыв подключения или секрета является исключением безопасности: ожидающая/повторная попытка останавливается с явной причиной; подмена другой моделью не происходит. Принудительный отзыв проверяется также перед принятием ответа.

Задание исполняется от имени разрешённой операции рабочей области с сохранённым инициатором для аудита. Выход инициатора из системы или прекращение его участия не отменяет уже принятую команду автоматически. Удаление/блокировка области, отмена запуска и отзыв ресурса проверяются перед следующим внешним действием и публикацией. Новое действие от имени бывшего участника невозможно.

Повтор после timeout может повторно оплатить внешний вызов. Если провайдер поддерживает идемпотентность или получение прежнего результата, адаптер использует это; иначе сохраняется неопределённый исход попытки. Технический расход включает страницы, длительность, provider/model, reported tokens и оценку стоимости с указанием её происхождения. Отсутствующие токены — неизвестны, не ноль. Это аналитика себестоимости, а не будущий финансовый ledger.

## Отмена, удаление и аудит

Отмена — запрос прекратить дальнейшую работу. Уже отправленный запрос может завершиться и стоить денег; отмена запрещает публикацию результата, но не обещает возврат стоимости. Устаревший worker не может обойти это поздним commit.

Удаление дела сначала закрывает доступ и ставит deletion intent/tombstone, затем повторяемый workflow отменяет работу и удаляет факты, снимки, источники и производные артефакты. Физическая очистка завершается только после проверки всех владельцев и выполняющихся попыток. До очистки tombstone защищает от «воскрешения» старым заданием. Политика хранения резервных копий и остаточных audit-метаданных описывается явно; удаление живых данных не выдаётся за мгновенное удаление всех backups.

Аудит фиксирует actor/scope, действие, ресурс, время, итог и correlation ID. Содержательные версии фактов хранятся у владельца фактов с его политикой удаления; общие логи и audit metadata не дублируют паспортные данные и тексты документов.
