# Runtime и диагностика

Статус: согласованный проект реализации, не свидетельство работающего размещения.

## Ответственность

`apps/api` владеет HTTP-транспортом, `apps/worker` — транспортом BullMQ,
`apps/web` — Next.js и вызовами API. `backend/runtime` собирает серверные
адаптеры для каждого процесса и закрывает созданные им ресурсы. Предметные
модули не зависят от HTTP и очереди. `@anyko/logger` владеет форматом событий,
но не конфигурацией процесса, транспортом хранения или политикой ротации.
Новые папки создаются вместе с работающим кодом, а не ради дерева.

## Конфигурация и жизненный цикл

Каждое приложение проверяет свою конфигурацию Zod при запуске. Секреты и их
значения не включаются в ошибки или логи. Runtime получает проверенные значения,
а не читает окружение самостоятельно. Публичные переменные сборки Next
отделены от серверной runtime-конфигурации; браузер использует относительный
путь `/api`.

Процесс проходит состояния starting, ready, degraded, stopping и stopped;
фатальная ошибка приводит к failed. Readiness API отражает его обязательные
зависимости. Readiness worker требует зарегистрированных обработчиков,
работающего consumer и доступного Redis. При недоступности Redis worker
становится degraded и восстанавливает соединение; liveness не объявляет
временный сбой причиной бесконечных перезапусков.

Остановка закрывает readiness, прекращает приём новых заданий, ожидает текущие
операции в пределах deadline и закрывает ресурсы. Deadline процесса меньше
grace period контейнера. Частично завершённый запуск также освобождает ресурсы.

## Очередь

Worker использует Redis и BullMQ. Envelope задания версионируется и проверяется
на границе потребителя. Для приёмки создаётся отдельное техническое задание и
producer в тесте или диагностической CLI; публичной постановки произвольных
заданий нет. Повторная доставка и остановка во время выполнения проверяются
на настоящем Redis. При реализации предметных задач действует транзакционный
outbox из [данных и заданий](data-and-jobs.md).

Redis очереди изолируется от остальных приложений, использует persistence и
`noeviction`. Настройки ожидания producer и consumer различаются; владельцы
учитывают также дополнительные соединения BullMQ. Версии и совместимость Bun
проверяются в реализации, а не предполагаются по текущей документации.

## События и серверный журнал

В локальной разработке sink принадлежит `scripts/run-local.mjs`: он запускает
API или worker с cwd приложения, передаёт сигналы дочернему Bun и сохраняет
stdout/stderr одновременно в терминале и `apps/<app>/.logs/runtime.log`.
В интерактивном терминале события stdout отображаются компактно с цветом по
уровню; `NO_COLOR` отключает цвет. При перенаправлении stdout остаётся исходным.
В файле и в stderr сохраняется исходный вывод без преобразования.
Общий logger продолжает писать в stdout, поэтому локальное хранение не меняет
контракт событий или production transport. Файл дописывается после перезапуска;
ротация ограничивает текущий файл 10 MiB и сохраняет три предыдущих. Один
launcher владеет файлом приложения; параллельный запуск того же приложения
требует отдельного каталога и в этот режим не входит. Docker запускает entry
point напрямую, без локального launcher.

API и worker используют общий `@anyko/logger`; серверный Next подключается при
появлении соответствующих событий. Pino пишет структурированные JSON-события
в stdout. Обязательные поля: версия схемы, время UTC, уровень, сервис,
окружение, release и имя события. Контекст запроса включает request ID, метод,
шаблон маршрута, статус и длительность; контекст очереди — job ID, тип,
попытку и correlation ID. Correlation ID связывает HTTP и обработку.

Логируются только разрешённые поля. Тела документов, запросов и ответов
провайдеров, cookies, ключи и полные значения env запрещены. Ошибки внешних
SDK проходят безопасное преобразование: маскирование известных путей не
очищает произвольные сообщения, stack или cause. Текст framework и аварийный
вывод сохраняются как сообщения с признаком формата, а не отбрасываются.

На отдельном сервере Anyko Docker отправляет вывод сервисов в journald с
устойчивыми метками проекта, окружения и сервиса. Persistent journal хранит
историю независимо от жизненного цикла контейнеров. Цель — до 14 дней в
пределах бюджета диска и резерва свободного места; доступная история может
быть короче. Размер бюджета определяется при подготовке конкретного сервера.
Ограниченная неблокирующая доставка допускает потерю технических событий при
переполнении, но не бесконечную блокировку приложений. Потеря сервера не
покрывается этой схемой.

Доступ агента предполагает отдельный SSH-ключ с принудительно заданной
командой чтения: без shell, PTY, forwarding, Docker socket и полного доступа к
системному журналу. Серверная команда самостоятельно применяет allowlist
Anyko, проверяет фильтры времени, сервиса и идентификаторов, ограничивает
объём и явно сообщает об усечении. Она не исполняет исходную SSH-команду как
shell. Доступ к диагностике и изменение конфигурации сервера являются
отдельными действиями при размещении.

## Dokploy и доказательства

Web, API и worker выпускаются как отдельные процессы одного выпуска; Redis и
журнал имеют независимый жизненный цикл. Внешний proxy направляет страницы в
web, `/api` — в API; worker и Redis не публикуются в интернет. Образы и
идентификаторы выпуска фиксируются, секреты предоставляются окружением.

При реализации проверяются: неверный env без раскрытия значения; настоящий
HTTP-запрос и связанное событие; обработка диагностического задания через
Redis; reconnect и остановка при активном задании; запуск Next; поиск записи
предыдущего выпуска после пересоздания контейнера и перезагрузки сервера;
ограничения доступа и объёма диагностики. Проверки фактического Dokploy,
серверного journal и восстановления не считаются пройденными до их выполнения
в соответствующей среде.
