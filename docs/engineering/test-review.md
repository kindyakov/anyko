# Проверка тестов, написанных агентом

Эти правила применяются к новым, существенно изменённым и удаляемым тестам. Процедура автора и независимого reviewer определена в [agent-workflow.md](agent-workflow.md). Тесты — проверяемый код, а их количество и зелёный статус не доказывают достаточность защиты.

## Что reviewer устанавливает для каждого изменения

1. **Требование:** какое наблюдаемое поведение или инвариант защищён и откуда он взят. Ожидаемый результат задан независимо от проверяемого алгоритма.
2. **Граница:** какая настоящая реализация исполняется. Mock подменяет внешнюю зависимость, а не предмет проверки. Проверка HTTP через настоящий сервер доказывает больше, чем вызов обработчика, но не доказывает production-размещение.
3. **Различимость:** какая конкретная ошибка изменит assertion. Успешный import, отсутствие исключения или вызов helper сами по себе не заменяют проверку результата, если контракт требует результата.
4. **Устойчивость:** какой допустимый внутренний рефакторинг тест должен пережить. Зависимость продуктового теста от имени файла или private-функции требует обоснования.
5. **Изменение защиты:** при удалении/ослаблении теста — где остаётся защита действующего требования или почему требование больше не действует.

Reviewer фиксирует короткое обоснование по группе однотипных тестов, без анкеты на каждый assertion. Если нет реального риска, новый тест не нужен. Для удаления внутреннего компонента проверяются оставшийся сценарий и ссылки; тест «этот файл отсутствует» не создаётся ради факта удаления. Отсутствие публичного endpoint, UI-действия или запрещённого поставляемого артефакта может быть настоящим требованием и проверяться.

Тесты анализатора исходников закономерно используют файлы и строки как вход. Они проверяют результат анализатора на допустимом и недопустимом примерах, а не запрещают рефакторинг продуктового кода. Snapshot уместен для стабильного согласованного результата; его обновление требует проверки содержимого, а не только принятия нового снимка.

## Глубина проверки по риску

| Изменение | Обязательное доказательство |
| --- | --- |
| Документация, оформление, внутренняя декомпозиция без изменения поведения | Проверки затронутой области и review; новый тест не обязателен |
| Новое обычное поведение | Сценарий с ожидаемым результатом и существенные ошибочные входы |
| Исправление воспроизводимой ошибки | По возможности failing case на старом поведении и passing case после исправления; отсутствие воспроизведения явно указано |
| Новый/изменённый критический инвариант доступа, денег, сохранности данных, конкурентности или удаления | Реальное исполнение соответствующей границы и доказательство, что тест обнаруживает нарушение именно этого инварианта |
| Новое/изменённое правило автоматического контроля | Плохой пример отклоняется, хороший проходит; для allowlist проверяется и разрешённое ребро |

Для критического инварианта одного static review недостаточно. Если требуемая среда недоступна, статус остаётся непроверенным; его нельзя заменить обещанием или unit-тестом mock-объекта. Выполнение интеграционного сценария не отменяет проверки смысла ожидаемого результата.

## Как доказать способность обнаружить ошибку

Использовать воспроизведение прежнего бага либо контролируемое нарушение в изолированной копии кода. Например: убрать tenant predicate, отключить проверку редакции или разрешить принятие устаревшей попытки. Критерий и ожидаемый assertion назвать до запуска; менять только относящееся к риску условие. Рабочий код, чужие изменения и production-данные для такого эксперимента не повреждать.

Записать: нарушенное правило, версию/снимок и команду, наблюдённое падение, затем успешный запуск исправной версии. Ошибка компиляции, отсутствующий импорт, timeout инфраструктуры или произвольный красный тест не считаются обнаружением предметной ошибки. При невозможности корректного эксперимента указать причину и недостающее доказательство; критическую проверку не объявлять завершённой.

Отрицательный вход проверяет обработку этого входа. Он сам по себе не доказывает, что тест заметит исчезновение защиты. Mutation testing может автоматизировать часть экспериментов; универсальный процент mutation score и отдельный runner сейчас не вводятся.

## Подсказки LLM

Семантическая подсказка получает итог `confirmed`, `rejected` с причиной или `needs-context`. Она не исправляет код автоматически и не заменяет тест/ревью. Отсутствие замечаний, пропуск файла, голосование моделей и высокая уверенность модели не доказывают корректность. Изменения тестов и контрольных конфигураций рассматриваются по тому же процессу, что production-код.
