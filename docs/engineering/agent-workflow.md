# Работа агентов и независимая проверка

## Автор изменения

1. Прочитать корневой `AGENTS.md`, применимые локальные инструкции, глоссарий и ADR затронутой области. Найти задачу/критерии и текущее состояние файлов. Прямое поручение пользователя достаточно для работы; отсутствие Issue не служит искусственным блокером. Задачи и спецификации, которые требуется вести в трекере, оформляются по [issue-tracker.md](../agents/issue-tracker.md).
2. До кода назвать владельца поведения, затронутые приложения/модули, разрешённые зависимости и данные. Записать наблюдаемый результат, источник требования, существенный риск и способ проверки. Источник — поручение, принятая спецификация/ADR или внешний контракт, не текущая реализация. Для малой правки достаточно нескольких предложений в задаче; отдельный документ не требуется. Если неоднозначность меняет продуктовое поведение, вынести конкретный выбор пользователю, а не решать его голосованием агентов.
3. Реализовать минимальный законченный сценарий в существующих границах. При изменении интерфейса обновить потребителей и тесты. При изменении архитектурного решения явно пересмотреть соответствующий ADR, не оставляя противоречия.
4. Выполнить применимые проверки из [quality.md](quality.md), изучить полный итоговый diff. Удалить неиспользуемый код, проверить зависимости, миграции, секреты и побочные изменения инструментов.
5. Передать конкретный снимок независимому reviewer: задача, критерии, границы diff, затронутые решения, результаты команд и ограничения проверки. Самооценка автора не является независимым review.
6. Исправить подтверждённые замечания. Повторить затронутые проверки и review изменённых участков; изменения общих интерфейсов расширяют повторную проверку на потребителей.
7. Сообщить итог: что изменилось, почему, доказательства по уровням, незакрытые ограничения. Не заявлять полноту CI/размещения по локальному тесту.

В общем checkout сохраняются чужие файлы, index и незакоммиченные изменения. Снимок незакоммиченного результата включает список файлов, включая untracked, и их content hashes; одного `git diff` недостаточно. Для commit-based review достаточно точных base/head commits. После изменения снимка старое заключение не распространяется автоматически на новые строки.

## Проверяющий агент

Проверяющий получает свежий контекст и читает правила и реальный diff. Для изменений кода он выдаёт два отдельных заключения. Один reviewer может выполнять оба; сложная миграция/доступ/конкурентность допускает дополнительную специализированную проверку. Для простого текста применимо облегчённое review.

**Product review:** выполнены критерии; основной и ошибочные сценарии понятны; данные и источники сохраняются; доступ ограничен; результат можно проверить. Интерфейс при изменении поведения проверен браузером либо явно указан отсутствующий browser proof.

**Code review:** верный владелец логики; типы и runtime-границы; нет обхода модуля/tenant scope; зависимости оправданны; результаты Knip/копирования рассмотрены; нет лишних абстракций и мёртвых путей; тесты способны обнаружить ошибку; миграция/очередь/удаление совместимы с эксплуатацией.

Reviewer сначала читает требование, его источник, diff и потребителей; объяснение автора использует как дополнительный материал. Новые, изменённые и удалённые тесты рассматривает по [test-review.md](test-review.md). Для изменения существенного риска самостоятельно выбирает контрпример и проверяет его; согласие с автором и смена модели не заменяют доказательство.

Заключение связывает Product и Code review с одним снимком. Для каждого критерия указывает конкретный тест/наблюдение либо отсутствие проверки. У команд записываются cwd, runtime, exit code и место лога; hash связывает результат с содержимым, но не удостоверяет независимость и качество рассмотрения. Достаточны задача, PR или итоговый отчёт; отдельный receipt на каждый тест не требуется.

Замечание содержит конкретное место, условие воспроизведения или нарушенный инвариант, влияние и приоритет. Стилистическое предпочтение, уже решённое Bun fmt, не блокирует работу. Для гипотезы reviewer указывает недостающую проверку вместо объявления непроверенного бага.

Успешное независимое review не заменяет автоматические проверки. Если reviewer недоступен, работа может быть подготовлена и проверена автором, но независимая приёмка отмечается `not run`, а не изображается завершённой.

## Изменение правил и инструкции

Один источник на правило: imports — конфигурация границ и объяснение в architecture/repository, формат — общий Bun fmt, критерии доказательства — quality. Локальные AGENTS содержат только отличия приложения и ссылки с условиями чтения. Они создаются вместе с реальным приложением и не копируют корневые правила.

Ослабление контроля рассматривается явно в Code review, вместе с точной причиной и областью. Агент может исправлять неверную конфигурацию; он не скрывает падение проверок заменой требования. Статус обязательной проверки остаётся незавершённым до исправления или принятого обоснованного исключения.

Это относится к удалению/ослаблению assertions, переносу границы mock, обновлению эталонов, расширению ignore, смене критериев и CI skips. Reviewer устанавливает, чем теперь защищено прежнее требование или почему оно отменено. Автор не принимает такое изменение единолично. При настроенной защите ветки результат подтверждает отдельный CI на итоговом commit; до её настройки ограничение процедурное. Заполненный шаблон PR и зелёный receipt не являются техническим разрешением на merge.

Публикация, доступы, миграции реальных данных и работа с секретами выполняются только в пределах поручения пользователя и правил окружения. Создание технического плана не является разрешением на production deploy или включение платежей.
