# Устройство репозитория

Это целевая структура. Директории создаются вместе с работающим кодом; дерево не означает, что каркас уже существует.

Принятые подходы: [ADR 0004](../adr/0004-code-organization.md). Web организован по features; backend — по предметным владельцам и вертикальным сценариям с портами/адаптерами. API и worker являются транспортными адаптерами этих сценариев.

## Приложения и пакеты

Один приватный Bun workspace, один корневой `bun.lock`, зависимости внутренних пакетов через `workspace:*`. Три приложения MVP; MinerU — внешний по отношению к TypeScript workspace сервис. Мигратор — одноразовая команда из release-образа, не четвёртое постоянно работающее приложение.

```text
apps/
  web/                     Next.js: пользовательский кабинет и SSR
  api/                     Elysia: HTTP, auth endpoint, транспортные адаптеры
  worker/                  Bun: очередь, dispatcher, восстановление заданий
packages/
  backend/                 серверные бизнес-модули, сценарии и адаптеры
  logger/                  общий серверный формат событий и безопасные поля
  contracts/               безопасные для браузера HTTP-схемы и DTO
  database/                Prisma schema, миграции, клиент и механизм транзакций
  ui/                      компоненты и токены интерфейса Anyko
  prettier-config/         @anyko/prettier-config: base, backend, frontend
  eslint-config/           @anyko/eslint-config: общие и средовые правила
  typescript-config/       @anyko/typescript-config: base, server, next, library
infra/
  compose/                 локальное окружение и первоначальное размещение
  containers/              определения сборки образов
  proxy/                   маршрутизация внешнего трафика
scripts/                   короткие команды инженерной обвязки
tests/
  e2e/                     сквозные сценарии работающих приложений
  fixtures/                синтетические документы и эталоны
docs/
  engineering/             правила разработки и эксплуатации
  adr/                     причины архитектурных решений
  agents/                  интеграции агентского процесса
  brand/                   существующие материалы бренда
.github/workflows/         CI при реализации каркаса
```

Семь пакетов — целевая стартовая граница, не требование создавать семь пустых библиотек. `ui` появляется вместе с первыми компонентами. Ни отдельный `utils`, ни `shared`, ни универсальный пакет для всех типов не вводятся. `work/` остаётся местом временных материалов и не становится runtime-зависимостью.

## Серверный пакет

```text
packages/backend/src/
  modules/
    access/                пользователи, участие, роли и политики доступа
    cases/                 жизненный цикл и реквизиты дела
    documents/             исходники, версии, разбор, источники и артефакты
    processing/            запуски, этапы, попытки, outbox, настройки подключения
    facts/                 кандидаты, подтверждения, конфликты и редакции
    templates/             готовые версии шаблонов и их требования к данным
    generation/            снимки входных данных и сформированные результаты
  workflows/               сценарии, связывающие публичные API модулей
  profiles/
    bfl/                   конкретные правила извлечения и проверки для БФЛ
  platform/                технические clock/storage/http адаптеры
  runtime/                 сборка зависимостей для API и worker
```

Пример выросшего предметного модуля:

```text
modules/facts/
  index.ts                 небольшой публичный API модуля
  domain/                  чистые правила, значения и переходы состояний
  application/             команды, запросы и нужные им узкие порты
  infrastructure/          реализации persistence и внешних интеграций
  tests/                   интеграционные проверки модуля
```

Небольшой модуль начинает с нескольких содержательных файлов. Подпапки появляются при разделении ответственностей; пустые `domain/application/infrastructure` не создаются ради шаблона. Unit-тесты располагаются рядом с проверяемым кодом. Интеграционные тесты могут знать внутреннее устройство своего модуля, но не становятся экспортом production-пакета.

`processing` управляет исполнением и состоянием, а профиль БФЛ — смыслом извлекаемых сведений. Сценарий в `workflows/` координирует модули; модули не импортируют сценарии. Registry запускаемых обработчиков собирается в `runtime/`, а не через сканирование файлов или динамическую загрузку произвольного кода.

Composition root в `backend/runtime` может импортировать `modules/<name>/infrastructure` для сборки конкретных адаптеров. Это единственное внешнее исключение из приватности модуля; private domain/application остаются закрыты. В HTTP-handler и worker-handler runtime не импортируется: сборка выполняется в entrypoint процесса или диагностической CLI.

## Структура запуска приложений

В корне `apps/api/src` и `apps/worker/src` остаётся `index.ts`, который вызывает
именованный bootstrap. HTTP, конфигурация процесса, CLI и тесты имеют разные
причины изменения и не складываются рядом с ним.

```text
apps/api/
  src/index.ts
  src/bootstrap/           start-api, env и конфигурация подключений
  src/http/app.ts          сборка HTTP-приложения и общие HTTP hooks
  src/http/routes/         auth, documents и будущие HTTP-адаптеры
  tests/                   тесты конфигурации и HTTP
apps/worker/
  src/index.ts
  src/bootstrap/           start-worker, env, ресурсы и остановка процесса
  src/cli/                 диагностические команды
  tests/                   тесты конфигурации процесса
packages/backend/
  src/runtime/index.ts     существующий публичный интерфейс сборки
  src/runtime/documents/   API/worker сборки сценария и unit-of-work
  src/runtime/diagnostics/ техническая диагностика очереди
  tests/integration/       проверки PostgreSQL/Redis и нескольких модулей
```

Новый предметный код добавляется владельцу в `modules`, связывающий сценарий —
в `workflows`, сборка конкретных реализаций — в соответствующую группу `runtime`.
В корень runtime не добавляются файлы каждого нового сценария. Пустые группы
для будущих billing/admin/agents заранее не создаются. Unit-тесты предметных
модулей остаются рядом с реализацией; интеграционные проверки не являются runtime.
Интеграционные `tests/integration/*.test.ts` могут собирать реальные infrastructure
адаптеры модулей, но не импортируют private application/domain. Это отдельное
проверяемое исключение для тестов, не расширение прав production-кода.

Импорт `backend/runtime` разрешён только в `bootstrap/start-api.ts`,
`bootstrap/start-worker.ts` и `worker/src/cli/diagnostic.ts`. Даже соседний
bootstrap/config не получает это исключение. Архитектурные fixtures проверяют
разрешённые точки сборки и запрещённые HTTP/config импорты.
Dependency-cruiser разрешает workspace-алиасы через `package.json exports`;
неразрешённый импорт `@anyko/*` является ошибкой. Контрольные примеры используют
как относительные пути, так и настоящие workspace-ссылки, чтобы алиас не обходил
правила доступа к runtime и database.

## Правила зависимостей

| Откуда | Что разрешено |
| --- | --- |
| `apps/web` | `contracts`, `ui`, свои features и средовые конфигурации |
| `apps/api` | `contracts`, публичные интерфейсы `backend`; `backend/runtime` только в bootstrap |
| `apps/worker` | публичные интерфейсы `backend`; `backend/runtime` только в bootstrap |
| Будущий `apps/admin` | административные HTTP-контракты, `ui`, свои features; доступ через API |
| `backend/workflows` | публичные интерфейсы модулей и профилей; узкий транзакционный порт |
| `backend/profiles` | чистые схемы/правила и явно разрешённые доменные value types; без I/O, Prisma, env, runtime и workflows |
| `backend/platform` | технические библиотеки; без предметных модулей, workflow и бизнес-решений |
| `module/application` | собственный domain, порты; явно перечисленные публичные интерфейсы другого модуля при отсутствии цикла |
| `module/domain` | собственные значения и чистые функции; без HTTP, БД, env и внешних SDK |
| `module/infrastructure` | собственные порты, `database`, необходимые технические адаптеры |
| `backend/runtime` | сборка всех серверных адаптеров; без бизнес-решений |
| `contracts` | Zod и переносимые значения; без `backend`, Prisma и секретов |
| `database` | Prisma и технические зависимости; без `backend` |
| `ui` | React и UI-зависимости; без API, БД и предметных сценариев |

В production-коде доступ к `database` имеют только persistence-адаптеры модулей, адаптер транзакции в `backend/runtime`, auth-адаптер и мигратор. Остальной bootstrap получает готовые сервисы из runtime. Публичные типы модулей не содержат Prisma/Elysia/Next типов.

Пакетные `exports` перечисляются явно: например, `@anyko/backend/facts`, `@anyko/backend/workflows`, `@anyko/backend/runtime`. Импорт через соседний `src/`, относительный выход в другой пакет и wildcard-экспорт всего сервера запрещены. Внутренние правила контролируются отдельной проверкой архитектуры, поскольку одних package exports недостаточно для файлов внутри пакета.

Каждое межмодульное ребро должно быть отражено в конфигурации проверки зависимостей и рассмотрено на review. Обратный импорт ради «быстрого исправления цикла» не допускается. Обычно связь переносится в workflow, который вызывает оба публичных интерфейса. Runtime-композиция не даёт права читать чужие таблицы.

## Frontend

```text
apps/web/src/
  app/                     маршруты, layout, metadata, сборка экранов
  features/
    cases/                 UI и действия по работе с делами
    document-upload/       загрузка и её состояния
    fact-review/           проверка фактов и источников
    generation/            запуск и скачивание результата
  lib/                     транспорт API, работа с сессией, средовые адаптеры
```

Маршрут компонует экран. Feature владеет пользовательским поведением; общие визуальные элементы берутся из `@anyko/ui`. Серверные компоненты читают данные через API с контекстом пользователя. Бизнес-операции не дублируются в Server Actions/Route Handlers. Конкретные серверные auth/proxy-интеграции допустимы только как транспорт, без собственного решения о правах и данных.

Это feature-based, без стандартных слоёв FSD. UI, состояние и HTTP-вызовы конкретной возможности находятся вместе. Features не импортируют private-файлы друг друга; общую композицию выполняет маршрут/экран. Server-only конфигурация и credentials остаются в `lib/server`, технический транспорт — в `lib/api`.

UI-проверка формы улучшает обратную связь, но сервер снова валидирует вход. Browser-safe DTO отличаются от доменной модели и модели хранения; это намеренные границы, а не запрещённое дублирование. HTTP-схема — источник TypeScript DTO, но не обязательная форма таблицы БД.

## Как добавлять новое

| Изменение | Место и обязательная граница |
| --- | --- |
| Новый шаблон | `templates`: immutable версия + совместимость данных; fixture генерации |
| Новый вид извлечения | `profiles/<name>` + типизированный обработчик; общие lifecycle-механизмы остаются в `processing` |
| Новая предметная возможность | `backend/modules/<name>`: владелец данных, публичные команды/запросы, тесты и разрешённые импорты |
| Новая таблица | В общей схеме `database`, с одним предметным владельцем, миграцией и правилами workspace/lifecycle |
| Новая интеграция | Infrastructure владельца; общий технический клиент выделяется после реального повторного использования |
| Новое приложение | `apps/<name>`, если нужны отдельная точка входа и жизненный цикл размещения |
| Новый сервис | ADR с причиной изоляции, владением данными, совместимостью протокола и способом восстановления |

Новая feature обычно не требует нового приложения или пакета. Перед выделением сервиса сначала проверяется возможность отдельной очереди или worker-пула на том же образе.
