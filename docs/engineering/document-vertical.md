# Первая вертикаль обработки документов

Реализованный локальный сценарий: закрытый вход → документ/фотография → приватный S3 source →
PostgreSQL metadata/run/outbox → BullMQ worker → MinerU → immutable result → UI.
Организация кода следует [ADR 0004](../adr/0004-code-organization.md).

## Запуск

Создайте игнорируемый корневой `.env` по `.env.example`. PostgreSQL и отдельная
тестовая база предоставляются локально. Не используйте для тестов рабочую БД.
Команда `bun run dev` поднимает Redis и S3, генерирует Prisma, применяет additive
миграции и создаёт локального пользователя. Если MinerU недоступен, запускается
подготовленное окружение из [инструкции MinerU](mineru.md). Первичная установка
MinerU выполняется отдельно по этой инструкции.

Откройте `http://localhost:3000`. Локальные email/password берутся из `.env`;
в репозиторий и журналы они не попадают. Повторное provisioning не меняет пароль
существующего пользователя. Публичная регистрация отключена. Сессии Better Auth
хранятся в PostgreSQL; membership проверяется при каждом обращении к данным.

В первой версии пользователь работает в первой доступной ему рабочей области.
Переключение областей и управление участниками не реализованы. Workspace из
браузерного запроса не используется как источник полномочий.

## HTTP и данные

`/api/auth/*` обслуживает Better Auth; `/api/session` возвращает пользователя и
рабочую область. `/api/documents` принимает multipart `file` до 20 MiB и UUID
`Idempotency-Key`; одинаковый вход возвращает прежний документ, иной — конфликт.
GET списка/документа и GET `/:id/result` проверяют scope. POST `/:id/retry`
создаёт новую редакцию запуска только после ошибки; история сохраняется.

Поддержаны PDF, DOCX, JPEG (`.jpg`/`.jpeg`), PNG, WebP и TIFF (`.tif`/`.tiff`).
Сервер проверяет расширение и сигнатуру содержимого, DOCX — также структуру ZIP
с ограничением размера распакованных данных. Произвольный ZIP с расширением DOCX
не принимается. MIME браузера не является источником доверия.

Оригиналы и результаты хранятся в приватном локальном S3-compatible RustFS.
Исходный объект неизменяем, результат записывается в ключ конкретной попытки.
Намерение загрузки сохраняется отдельно: очистка не удаляет опубликованный
артефакт при неопределённом исходе commit. PostgreSQL является источником
состояния. Потерянное Redis-задание повторно доставляется reconciler.

MinerU запускается локально, версия 4.1.7, stateless HTTP-адаптер поверх Python SDK. PDF и фотографии
обрабатываются в Basic с автоматическим OCR, DOCX — нативным Flash-парсером
текста и таблиц. OCR картинок, вложенных в DOCX, этим сценарием не гарантируется.
HEIC/HEIF пока не принимаются. Это не оценка качества на клиентском корпусе.
UI имеет режимы «Просмотр» и «Markdown»: заголовки, списки, GFM/очищенные HTML-таблицы,
изображения и LaTeX через KaTeX. Inline-формулы используют `$...$`, блочные —
отдельные строки `$$`, содержимое и закрывающую строку `$$`. Произвольный HTML,
внешние изображения и опасные команды KaTeX не исполняются.
Страницы, координаты источников,
извлечение фактов LLM и генерация итогового DOCX остаются следующими возможностями.

## Артефакт и изображения

Stateless MinerU SDK отдаёт ZIP. Anyko сохраняет `result.json` с Markdown,
версией и manifest изображений, а каждое JPEG/PNG/WebP — отдельным приватным S3
объектом: `results/<workspace>/<run>/<attempt>/images/...`. В JSON находятся
только key, MIME, size и checksum, без Base64. `DocumentArtifact` регистрирует
владение каждым объектом до записи, включая незавершённые попытки.

API результата возвращает авторизованные `/api/documents/:id/images/:index`.
Маршрут изображения читает его метаданные из БД и только сам файл из S3, без
загрузки Markdown. Проверяются сессия и рабочая область; ответы — `no-store` и
`nosniff`. Пределы: 32 изображения, 3 MiB каждое, суммарно 8 MiB, JSON до 5 MiB.

Для существующих данных предусмотрен `bun run artifacts:migrate --applications-stopped --storage-requests-drained`: при остановленных
API/worker он переносит Base64 в файлы, переключает manifest и удаляет старые JSON
и legacy staging-копии. Картинки, ранее полностью отброшенные адаптером, восстановить
из Markdown нельзя — для них нужна новая загрузка исходника.

## Удаление

`DELETE /api/documents/:id` после подтверждения в UI возвращает 202. Транзакция
ставит tombstone `deletedAt` и аннулирует активные попытки. Список, текст,
картинки и повторный запуск сразу перестают быть доступны. Проверка публикации
и удаление сериализуются на строке документа; поздний worker не возвращает его
к жизни. Повторный DELETE своей tombstone идемпотентен; чужой ID даёт 404.

202 означает только начало. UI опрашивает `GET /api/documents/:id/deletion` и
закрывает подтверждение лишь при `deleted`.
Незавершённые удаления также возвращаются в `GET /api/documents` отдельным списком
UUID/status/createdAt без имени и содержимого: UI восстанавливает их после F5 и
опрашивает до завершения. Статус `needs-recovery` не исчезает при закрытии вкладки.

Worker подтверждает очистку всех
ProcessorAttempt, ждёт завершения writers, удаляет оригинал, изображения, manifest
и артефакты всех попыток, проверяет отсутствие каждого объекта через S3 HEAD.
Затем транзакция физически удаляет SourceDocument, ProcessingRun/outbox,
DocumentArtifact, ProcessorAttempt и staging-записи. Остаётся только техническая
DocumentDeletion: UUID, workspace, request UUID и время завершения — без имени,
checksum, содержимого, изображений или storage keys. Повторный запрос не воскрешает
старую операцию. Удаление не ждёт часового orphan sweep.

Записи и удаление сериализуются PostgreSQL session advisory locks без открытой
SQL-транзакции на время S3/OCR. Потеря lock отменяет дальнейшее I/O. DocumentIo
не позволяет объявить удаление завершённым при ещё активном writer, даже если
его DB-сессия потеряна. Неопределённый исход PUT сохраняет durable uncertainty:
статус `needs-recovery`, а не ложное `deleted`.

Recovery — только после подтверждённой остановки всех API/worker и завершения
запросов на стороне S3 (для self-hosted storage допустим контролируемый restart).
Команда `bun run documents:recover-writes --applications-stopped --storage-requests-drained`
подтверждает очистку processor attempts и снимает writer markers. Эти флаги —
явное подтверждение оператора, не автоматическая проверка supervisor. По TTL или
отсутствию DB-сессии markers не снимаются. Затем обычный worker завершает очистку.

Поддерживается только unversioned S3: startup проверяет bucket versioning и
отклоняет Enabled/Suspended, где DELETE оставляет старые версии. Stateless SDK
не использует Tasks/FileStore cache, все source/temp-файлы живут в управляемом
каталоге попытки; DELETE ждёт настоящего завершения OCR и его удаления. При
restart остатки очищаются до открытия HTTP. Старый Tasks uploads-кэш очищается
однократно при переходе после остановки старого сервиса. Веса моделей не содержат
документы и не удаляются. Отдельные внешние резервные копии не создаются приложением.

## Проверка

`bun run verify:fast` проверяет types, lint, зависимости, HTTP/proxy протоколы,
unit/config и инженерную обвязку. Генерация Prisma обязательна перед проверкой
свежего checkout: `bun run db:generate`.

При явных `TEST_DATABASE_URL` и `TEST_REDIS_URL` запускаются
`bun run test:documents:integration` и `bun run test:access:integration`.
Проверяются настоящие PostgreSQL/Redis; parser/storage в этих тестах контролируемые.
`bun run smoke:document` использует запущенные web/API/worker/S3/MinerU и
синтетический `work/mineru/smoke-basic.pdf`, который создаёт MinerU smoke.
Для другого входа: `bun run smoke:document work/mineru/smoke-basic.docx`.
Синтетические DOCX и фотографии создаются командой из инструкции MinerU.

CI поднимает PostgreSQL/Redis, генерирует клиент и применяет миграции к изолированной
тестовой БД. В обычном CI нет загрузки моделей и реального OCR. Серверное размещение
и полное удаление дела с будущими фактами/генерациями этой вертикалью не подтверждаются.
