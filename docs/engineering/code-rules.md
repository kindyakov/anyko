# Правила написания кода

Правила обязательны для агентов и людей. Автоматизирована часть контроля; применимость конкретной проверки отражена в [README](../../README.md). Порядок проверки и исключений — в [quality.md](quality.md).

## Типы и границы данных

- TypeScript с `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`; средовые настройки наследуются из `@anyko/typescript-config`.
- HTTP-вход, env, задания очереди, ответы OCR/LLM и сохранённый JSON неизвестной версии входят как `unknown`. Проверка Zod выполняется на соответствующей границе; внутрь передаются проверенные значения.
- Публичные интерфейсы модулей имеют явные входы и результаты. Локальные переменные используют вывод типов; повторять тип каждой переменной не требуется.
- `any`, `as unknown as`, non-null assertions и подавления ошибок не служат способом завершить задачу. Неизбежная нетипизированная интеграция изолируется в одном адаптере с runtime-проверкой и узким документированным исключением.
- `as const` и проверка через `satisfies` допустимы. Приведение, утверждающее непроверенный факт о данных, требует проверки либо изменения интерфейса.
- Состояния моделируются discriminated unions; невозможные сочетания флагов не становятся API. Переходы перечисляются явно, ветвления проверяются на полноту.
- `undefined`, отсутствующее поле, `null`, неизвестное значение и подтверждённое отсутствие объекта имеют разные значения в контракте. Денежные суммы и календарные даты используют предметно определённое представление; float не является форматом расчёта задолженности.

## Ответственности и интерфейсы

HTTP-handler валидирует вход, получает доверенный контекст, вызывает сценарий и отображает результат в HTTP. Worker-handler разбирает envelope, получает scope исполнения и вызывает сценарий. Оба не содержат правил сопоставления фактов, SQL или сборки DOCX.

Use case отвечает за конкретную команду или запрос, а не за все операции сущности. Domain-код получает часы, идентификаторы или значения явно, когда это влияет на поведение; не читает скрытое глобальное состояние. Инъекция зависимостей — обычные функции и объекты с узкими интерфейсами. DI-контейнер и generic repository не вводятся без отдельной причины.

Интерфейс адаптера описывает потребность модуля (`loadConfirmedRevision`), а не произвольные операции над всеми таблицами (`queryAnything`). Обёртка, только перенаправляющая вызов и не создающая полезную границу, не считается архитектурой.

Общая логика выделяется, когда совпадают смысл, правила изменения и владелец. Сходство нескольких строк в двух разных предметных контекстах само по себе не требует объединения. Копирование одного бизнес-правила в API, worker и UI исправляется переносом правила к серверному владельцу; UI может иметь отдельную предварительную проверку удобства ввода.

## Ошибки и побочные эффекты

- Ожидаемые результаты — типизированные коды: отсутствие доступа, конфликт редакции, невалидный документ, отклонённое состояние. Transport отображает их в стабильные ответы с correlation ID.
- Неожиданные исключения доходят до контролируемой границы и попадают в очищенный журнал. Catch без действия и успешный ответ после провала операции запрещены.
- Повторяются только распознанные временные ошибки, с лимитом, задержкой и deadline. Бесконечный retry, скрытая смена провайдера или повтор постоянной ошибки не допускаются.
- Каждая операция I/O имеет timeout и ограничение параллелизма. Отмена и неизвестный исход внешнего вызова различаются.
- Конфигурация процесса проверяется при старте; бизнес-настройки провайдера версионируются в БД. Секреты не включаются в DTO, исключения, snapshot-тесты и обычные логи.
- Технический logger общий по формату; модули передают идентификаторы операции, не полный документ или объект запроса.

## Зависимости и читаемость

Версии runtime и инструментов закрепляются при первом каркасе. Обновления lockfile сопровождаются проверкой соответствующей области; обновление строгих lint-конфигураций рассматривается как изменение правил. В runtime-пакете объявляются его прямые зависимости, даже если библиотека уже установлена соседним пакетом.

Prettier отвечает за стиль; ESLint — за ошибки и правила. Базовые настройки форматирования едины для frontend/backend; frontend-export может добавлять сортировку Tailwind-классов после проверки совместимости. Пакеты не копируют конфигурацию и не меняют стиль без общего решения.

Имена файлов и папок — `kebab-case`, React-компонентов и типов — `PascalCase`, функций и переменных — `camelCase`. Используются термины [глоссария](../../GLOSSARY.md). Комментарии объясняют причину, ограничение внешней системы или нетривиальное правило; не пересказывают код.

Крупный файл, длинная функция, глубокое ветвление или множество зависимостей — повод проверить ответственность на review. Универсального лимита строк нет: искусственное дробление, цепочки пересылающих функций и многослойные абстракции также являются недостатками.

Неиспользуемые экспорты, старые варианты реализации и закомментированный код удаляются вместе с заменой. Generated/vendor-файлы маркируются и исключаются адресно; ручные изменения generated-кода заменяются изменением источника генерации.
