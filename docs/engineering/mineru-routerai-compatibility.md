# MinerU и RouterAI: граница совместимости

Дата проверки: 5 ноября 2026. Исследовательская записка, не принятое архитектурное решение и не отчёт о работающей интеграции.

## Вывод

Удалённый VLM в MinerU возможен без локальных весов VLM. Однако OpenAI-compatible HTTP сам по себе не делает обычную vision-модель заменой специализированной модели MinerU. Для Anyko с условием «генеративный inference только через RouterAI» обоснованный следующий вариант — сохранить Basic OCR / Flash DOCX и добавить отдельное описание извлечённых изображений через RouterAI в сценарии обработки. Это предложение, ещё не реализация.

В публичном каталоге RouterAI на момент проверки не обнаружено модели с `MinerU` или `opendatalab` в имени/ID. Это ограничение проверенного публичного каталога, а не доказательство невозможности частного подключения или будущей поддержки. [Публичный каталог RouterAI](https://routerai.ru/api/v1/models).

## Что проверено

- В установленном окружении: MinerU **4.1.7**, `mineru-vl-utils` **2.0.8**; прочитан исходный код SDK без загрузки моделей и без создания inference-клиента.
- Прочитан текущий [процессор Anyko](../../infra/mineru/processor.py): PDF/изображения используют `basic`, DOCX — `flash`, всегда `ocr_mode='auto'`, `image_analysis=False`.
- Публичный GET каталога RouterAI выполнен без авторизации 2026-11-05T16:42:46Z: 595 моделей, 222 объявляют image input и text output; поиск `MinerU|opendatalab` по имени/ID дал 0. Сводка локальной проверки: `work/routerai-compatibility/catalog-summary.json`; это временный материал, не runtime-зависимость.
- Проверена сборка URL чистыми методами установленного SDK: выполнялись только извлечённые AST-функции нормализации, без конструктора HTTP-клиента, сетевого запроса или импорта модели.
- Не выполнялись платные/авторизованные inference-запросы, реальные OCR-прогоны, загрузка весов, установка зависимостей или production-проверка.

## Два разных контракта

Официальная документация разделяет document parsing API и удалённый VLM inference endpoint. `model.vlm.server_url` убирает необходимость локальных весов VLM; потребность в малых моделях зависит от tier. Для Basic малые OCR/layout-модели всё равно нужны. Поэтому «без локальной VLM» выполнимо, а «вообще без локальных моделей» не описывает текущий Basic. [MinerU: Model Source](https://opendatalab.github.io/MinerU/usage/model_source/).

Нативный клиент работает не как универсальный prompt-to-Markdown адаптер. Официальный `mineru-vl-utils` предназначен для MinerU Vision-Language Model; пример HTTP-сервера запускает `opendatalab/MinerU2.5-2509-1.2B`. Клиент выполняет layout detection, затем распознавание отдельных блоков; результат содержит типы блоков, bbox и содержимое. Официального обещания подставить любую общую vision-модель вместо MinerU в проверенных источниках нет. [README mineru-vl-utils](https://github.com/opendatalab/mineru-vl-utils).

Установленный `mineru_vl_utils/mineru_client.py:28–85,300–332,1040–1051` требует layout-вывод вида:

```text
<|box_start|>100 200 800 900<|box_end|><|ref_start|>text<|ref_end|><|rotate_up|>
```

Координаты задаются целыми числами 0–1000. Встроенные короткие команды — `Layout Detection:`, `Text Recognition:`, `Table Recognition:`, `Formula Recognition:`, `Image Analysis:`. Если ответ не содержит ожидаемой грамматики, layout-парсер не превращает обычное описание картинки в блоки: он логирует несовпадение и может вернуть пустой список. Это подтверждено чтением установленного кода; качество ответа конкретной модели RouterAI не тестировалось. [Первичный исходник клиента](https://github.com/opendatalab/mineru-vl-utils/blob/main/mineru_vl_utils/mineru_client.py).

Следовательно, замена только URL/model name не подтверждена. Теоретически возможен отдельный адаптер, переводящий ответы общей vision-модели в нужную структуру, но он потребует своей логики layout, распознавания и проверки качества. Это уже отдельная интеграция, а не документированная совместимость готового MinerU backend.

## HTTP и `/api/v1`

Установленный `mineru_vl_utils/vlm_client/http_client.py:90–136,242–402`:

| Часть                    | Требование                                                                                                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Discovery                | `GET .../v1/models`, ответ с `data[].id`; явное имя проверяется по каталогу, без имени ожидается ровно одна модель                                                      |
| Inference                | `POST .../v1/chat/completions`, `model`, `messages`, изображения через `image_url.url` с data URL                                                                       |
| Авторизация              | Bearer header; MinerU config предоставляет отдельные VLM API key/model поля                                                                                             |
| Ответ                    | HTTP 200, JSON object, непустой `choices`, `choices[0].message.content` как строка или null; обычно `finish_reason='stop'`, `length` по умолчанию отклоняется           |
| Дополнительные параметры | По умолчанию temperature 0, top_p 0.01, top_k 1, repetition_penalty 1, `vllm_xargs.no_repeat_ngram_size=100`, `skip_special_tokens=false`; штрафы зависят от типа блока |

Отправка этих дополнительных параметров RouterAI и сохранение специальных маркеров конечным провайдером здесь не подтверждены. Сам SDK содержит отдельную обработку имён, начинающихся с `gpt`, но это не универсальная гарантия для router-prefixed IDs. [Первичный HTTP-клиент](https://github.com/opendatalab/mineru-vl-utils/blob/main/mineru_vl_utils/vlm_client/http_client.py).

В версии 4.1.7 проверен `mineru/config.py:531–557`: config сохраняет proxy prefix, удаляет конечный `/v1` и добавляет завершающий `/`. Результаты локального выполнения чистых методов:

| Вход                         | Прямой HttpVlmClient: chat URL                | Через MinerU config: chat URL                 |
| ---------------------------- | --------------------------------------------- | --------------------------------------------- |
| `https://routerai.ru/api/v1` | `https://routerai.ru/api/v1/chat/completions` | тот же                                        |
| `https://routerai.ru/api/`   | `https://routerai.ru/api/v1/chat/completions` | тот же                                        |
| `https://routerai.ru/api`    | `https://routerai.ru/v1/chat/completions`     | `https://routerai.ru/api/v1/chat/completions` |

Таким образом, у проверенной версии `/api/v1` само по себе не является блокером. Риск потери `/api` возникает при прямом использовании низкоуровневого клиента с `/api` без завершающего слеша. В config этот случай нормализуется. Указание RouterAI на `/api/v1/chat/completions`, Bearer и base64 `image_url` совпадает с основным wire-форматом клиента; совместимость всех параметров и модельной семантики этим не доказывается. [RouterAI: изображения](https://routerai.ru/docs/guides/overview/multimodal/images).

## Практический вариант для Anyko

Предложение: Basic OCR для PDF/фотографий и Flash для DOCX → текст и доступные изображения → отдельный RouterAI vision-запрос для описаний/диаграмм → результат обработки. Для отдельно загруженной фотографии входом vision должен быть её оригинал: нельзя рассчитывать, что Basic экспортирует всю фотографию обратно в `images/`. Для PDF можно использовать извлечённые иллюстрации; покрытие извлечения embedded images из DOCX пока не доказано и требует отдельной проверки. Генеративная часть работает только через RouterAI; малые локальные модели Basic сохраняются. Наличие модели с image input позволяет рассматривать её кандидатом, но выбор модели требует оценки на разрешённом корпусе, времени и стоимости. Кандидаты из проверенного каталога: `google/gemini-2.5-flash-lite`, `google/gemini-2.5-flash`, `qwen/qwen3-vl-30b-a3b-instruct`; качество не сравнивалось. [Каталог](https://routerai.ru/api/v1/models), [vision API](https://routerai.ru/docs/guides/overview/multimodal/images).

Сценарий и состояние этапа должны принадлежать backend-модулям обработки/документов, RouterAI — отдельный infrastructure adapter, worker — запускать сценарий через публичный API. Описания необходимо связывать с исходным изображением и версией обработки; не подменять ими исходник или OCR. Сохранять текущие Markdown/изображения и exports, регистрировать новые артефакты, учитывать отмену, tombstone и запоздавшие ответы при удалении. Это следует из существующих [границ модулей](repository.md) и [жизненного цикла документов](document-vertical.md), а не из якобы готовой функции MinerU.

Сейчас Anyko экспортирует только Markdown и изображения; страницы и bbox не включены в текущий контракт результата. Их появление потребует явного расширения контракта. OCR вложенных DOCX-картинок и полнота отбора иллюстраций текущим режимом не гарантируются. Локальное удаление артефактов также не доказывает удаление данных на стороне внешнего провайдера; перед заявлением о полном удалении при RouterAI потребуется проверить условия и возможности соответствующего сервиса. [Текущая вертикаль](document-vertical.md), [инструкция MinerU](mineru.md).

Если RouterAI позднее предоставит специализированный MinerU endpoint или подтвердит эквивалентную модель, можно отдельно проверить нативный remote VLM: точный model ID, каталог, параметры, layout tokens, таблицы/формулы/картинки и стоимость. На текущих доказательствах нельзя обещать такой режим одной настройкой и нельзя утверждать, что он принципиально невозможен.
