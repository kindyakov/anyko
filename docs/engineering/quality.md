# Проверка качества

Статус: целевой контракт качества. Фактически реализованная часть команд указана в [README](../../README.md), а их точный состав — в manifests и CI. Интеграционные, E2E и release-проверки ещё предстоит реализовать.

## Инструменты и обязательность

| Проверка | Инструмент | Условие принятия |
| --- | --- | --- |
| Форматирование | Prettier, общий пакет конфигурации | Нет расхождений |
| Типы | TypeScript `tsc` | Нет ошибок в production и тестовом коде |
| Локальные правила | ESLint flat config + typescript-eslint `strictTypeChecked` | Нет необработанных нарушений |
| Мёртвые файлы/экспорты/зависимости | Knip по workspace | Нет необоснованных находок |
| Границы и циклы | dependency-cruiser | Нет запрещённых рёбер, в том числе type-only обходов |
| Копирование | jscpd | Отчёт для Code review; каждая новая содержательная копия оценена |
| Backend unit/integration | Bun test | Ожидаемое поведение на выбранном runtime |
| React component tests | Vitest + React Testing Library | Поведение компонентов через публичный интерфейс |
| Сквозные проверки | Playwright | Основные сценарии на запущенных приложениях |
| Инструкции и конфиги | Небольшая проверка ссылок/manifests/scripts | Нет битых указателей и выдуманных команд |

Prettier не заменяет lint; Knip не доказывает, что каждая исполняемая ветка нужна; dependency-cruiser не понимает бизнес-смысл. jscpd не блокирует сборку одним процентом совпадений и не требует объединять независимые модели. Его отчёт обязателен при изменениях кода, выводы фиксируются в review.

Используются штатные возможности инструментов. Собственная система политик с DSL, подписанными attestations и универсальным runner для MVP не нужна. Маленькие scripts допустимы для связывания команд и проверки конкретного инварианта.

Версии инструментов закрепляются. У `strictTypeChecked` набор правил может меняться вне major-релиза, поэтому обновление рассматривается отдельно: [typescript-eslint configs](https://typescript-eslint.io/users/configs/). Knip настраивается по фактическим workspace/entry points, включая Next, worker, конфиги и scripts; экспорты публичных entry points проверяются с учётом реальных потребителей. [Knip workspaces](https://knip.dev/features/monorepos-and-workspaces).

## Три уровня проверки

| Целевая команда | Содержание | Когда обязательна |
| --- | --- | --- |
| `verify:fast` | format, typecheck, lint, boundaries, Knip, docs/config checks, unit/component; отчёт копий для review | Для каждого изменения кода; сначала весь небольшой workspace |
| `verify` | fast + integration с PostgreSQL/Redis/S3, сборки, E2E; контролируемые OCR/LLM fixtures | Для принятия изменений приложения в основную ветку |
| `verify:release` | production images, миграции, startup/readiness, smoke на Bun, проверка совместимости старой/новой версии заданий | Перед выпуском соответствующего релиза |
| `eval:documents` | Реальные MinerU/LLM и представительный разрешённый корпус | Перед пилотом и при изменении parser/model/prompt/extraction schema |

CI — GitHub Actions. Основная ветка получает required checks после реализации workflows и настройки репозитория; локальные hooks лишь ускоряют обратную связь. Эта документация не включает branch protection автоматически. Проверки не выполняют тихих автоисправлений: исправление — отдельный diff с повторной проверкой.

Full verify запускается на pull request/кандидате изменения; публикация приложения отдельна. Docs-only изменение проходит проверку затронутых ссылок/инструкций и review, без искусственного запуска OCR. Миграция, auth, очередь или общие контракты расширяют область проверки. Пропуск возможен только с объяснением неприменимости, а не из-за отсутствия Docker или времени.

Оптимизацию по affected packages вводить после измерения времени CI. Она учитывает обратные зависимости и изменения конфигураций; до этого проверяется весь небольшой workspace. CI использует изолированные данные и секреты окружения, без доступа к документам production.

## Границы тестовых сред

Backend unit и integration исполняются на Bun. Vitest/Playwright и другие dev tools могут запускаться на закреплённом поддерживаемом Node; это не меняет production-runtime приложения. В отчёте явно указано, какой runtime проверялся. Корневая команда вызывает scoped suites и не запускает голый `bun test` по всему репозиторию, чтобы не подбирать файлы Vitest/Playwright.

Async Server Components проверяются через реально запущенный Next и Playwright, а не имитируются Vitest: [ограничение Next/Vitest](https://nextjs.org/docs/app/guides/testing/vitest). E2E проходит через тот же proxy/API-path и cookie-механизм, что размещённое приложение.

## Что тестируем

- **Domain/unit:** деньги и даты, неизвестное/отсутствующее, сравнение сведений, переходы состояний, запрет перезаписи подтверждения. Часы/ID детерминированы там, где это влияет на правило.
- **Integration:** реальные ограничения PostgreSQL, scope доступа, транзакции/outbox, очередь, S3 lifecycle, retry и конкурентные изменения. Мок Prisma не доказывает корректность SQL/ограничений.
- **API/contract:** положительный и отрицательный вход, отсутствие прав, конфликт редакции, стабильные ошибки, поддержанные версии. Runtime-схемы проверяются с неверными данными, а не только TypeScript-объектами.
- **UI:** формы, ошибки, загрузка и ожидание; взаимодействие через роли и доступные названия. Layout, маршруты и сессии проверяются браузером.
- **DOCX:** значения и структура по fixture, отсутствие незаполненных обязательных тегов, затем визуальная проверка длинных ФИО/адресов и многостраничных таблиц. Побайтовое равенство ZIP не заменяет проверку документа.
- **Реальные модели:** важные поля, evidence, пропуски таблиц, конфликтующие данные, стоимость и время. Критерии корпуса фиксируются до сравнения; успешная Zod-валидация не означает корректное извлечение.

Обязательная матрица отказов для первой рабочей вертикали: повтор доставки; crash после DB commit до Redis; временная недоступность Redis; просроченная попытка после новой; timeout провайдера с неизвестным исходом; правка юриста во время обработки; удаление во время внешнего вызова; запрет доступа между двумя рабочими областями; восстановление после перезапуска worker; миграция с предыдущей схемы.

Фикстуры синтетические или явно разрешённые и обезличенные. Ни реальные паспорта, ни ключи не коммитятся. В обычном CI нет платных запросов LLM; live eval использует отдельные лимиты и разрешённый корпус. Непредсказуемый внешний ответ не делает детерминированный CI нестабильным.

Регрессионный тест воспроизводит исправляемое поведение. При удалении feature удаляются её тесты и входы, а не сохраняется мёртвая реализация ради покрытия. Общего процента покрытия для всех файлов нет; критические правила должны иметь позитивные, негативные и конкурентные сценарии по риску. Тесты не копируют алгоритм реализации для вычисления ожидаемого значения.

Обязательная смысловая оценка новых/изменённых тестов, критерии проверки их способности обнаружить ошибку и исключения по риску определены в [test-review.md](test-review.md). Эффективность самого reviewer проверяется на [контрольных примерах](review-cases/README.md); это отдельная процедура, а не автоматически пройденная часть CI.

## Проверка самого контроля и исключения

Новый запрет импортов имеет маленькие разрешённый и запрещённый примеры: контроль обязан пропустить первый и отклонить второй. Docs-check проверяет существование относительных ссылок, указателей AGENTS и команд после появления manifests; не анализирует стиль русских предложений. Generated/vendor/brand originals исключаются адресно, чтобы инструменты не меняли сохранённые исходники.

Исключение из type/lint/Knip/import правила указывает точный файл/символ, причину, ответственного, проверку риска и условие удаления. Комментарий располагается у настройки, а долгоживущее исключение связано с GitHub Issue. Широкий ignore папки ради одной ошибки не принимается. Reviewer проверяет изменение исключения отдельно; автор не считает ослабление правила доказательством исправления.

## Доказательства

Отчёт различает: static, unit, integration, build, browser, live extraction, release smoke и production. Для каждого — `passed`, `failed`, `not run` или обоснованное `not applicable`. Отсутствующий инструмент/сервис и пропущенный обязательный job не считаются успехом. Локальный зелёный тест не означает успешное размещение.

Дополнительные первичные источники: [dependency-cruiser](https://github.com/sverweij/dependency-cruiser), [jscpd](https://github.com/kucherenko/jscpd), [Bun test](https://bun.sh/docs/test), [Playwright](https://playwright.dev/docs/best-practices), [Prettier shared configs](https://prettier.io/docs/sharing-configurations).
