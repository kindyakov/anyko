## Итог технических дебатов

| Альтернатива                                  | Решение и причина                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Микросервисы сразу / неразделённый backend    | Модульный монолит с проверяемыми границами; отдельные процессы по нагрузке                    |
| Пакет на каждую сущность / один общий shared  | Один серверный пакет с предметными модулями; отдельные пакеты для реальных границ потребления |
| Полный SaaS сразу / изоляция после пилота     | Владение рабочей областью и вход с начала; самостоятельная регистрация и биллинг позднее      |
| Общий Prisma client доступен любому коду      | Только persistence-адаптерам; каждый модуль владеет своими таблицами                          |
| Только queue.add после сохранения             | PostgreSQL outbox + восстановление + идемпотентное принятие результата                        |
| Один тестовый runner любой ценой              | Backend проверяется на Bun; frontend-инструменты работают на поддерживаемой ими среде         |
| Нулевое дублирование / произвольный общий код | Отчёт о копиях и смысловой review; общая абстракция появляется после проверки её назначения   |
| Агент сам написал и сам принял                | Автопроверки и отдельный проверяющий с продуктовым и инженерным заключениями                  |
| Сразу создавать admin, billing и agent apps   | Фиксировать точки расширения; создавать код при появлении реализуемого сценария               |

## Порядок первого воплощения

Сначала workspace и общие конфигурации, затем один вертикальный сценарий через web → API → БД/outbox → worker → результат. На нём проверяется Bun и вводятся реальные quality gates. После этого расширяется предметная обработка MVP, затем пилотное размещение с доступом, восстановлением и наблюдаемостью. Подготовка полного SaaS не блокирует пилот и не подменяет его.
