# Архитектура серверной части: модули, доверенный scope, HTTP по контрактам и реестр заданий

16 ноября 2026. Уточняет разделы «API и worker» и «Backend» [ADR 0004](0004-code-organization.md) и границы пакетов из [repository.md](../engineering/repository.md). Модульный монолит [ADR 0001](0001-modular-monolith.md), правила данных и доставки из [data-and-jobs.md](../engineering/data-and-jobs.md) сохраняются.

## Контекст

Первая вертикаль доказала сценарий, но внутренняя структура сервера сложилась под один экран и два конвейера:

- **Scope.** `access.session` выбирает первое участие пользователя (`findFirst` по `workspaceId`); каждый маршрут повторяет `if (!session) throw new WorkError('FORBIDDEN')`; единственная проверка роли (`canManage` = owner) вызывается из маршрута. Сценарии получают `workspaceId: string`, который ничем не отличается от непроверенного значения из URL.
- **Ошибки.** `http/app.ts` переводит `WorkError` и `DocumentError` в статусы вложенными тернарными операторами; каждый новый модуль добавит ветку. Коды не перечислены в `contracts` (`code: string`), web не может обработать их исчерпывающе.
- **Транспорт.** Маршруты вручную разбирают JSON и UUID, не описывают ответы, не проверяют их и не публикуют OpenAPI. Session/origin hooks дублируются в `documents` и `works`; версии API нет.
- **Владение сценариями перевёрнуто.** Интерфейс `WorkApi` (12 операций) объявлен в `modules/works`, а реализован в `workflows/works/api.ts`; сам модуль `works` не содержит логики. `workflows/works/execute.ts` (431 строка) совмещает шаги запуска, вызовы модели и генерацию.
- **Сервер зависит от HTTP DTO.** 22 файла `backend` импортируют `@anyko/contracts`; workflow вызывает `workResponseSchema.parse`; facts/templates/generation используют HTTP-типы как доменные. `contracts/work-fields.ts` (328 строк) содержит правила профиля БФЛ: изменение профиля становится изменением HTTP-контракта и попадает в браузерный бандл. Единый `export *` отдаст будущие административные схемы пользовательскому web.
- **Композиция.** API-процесс создаёт четыре клиента Prisma (access, documents, works и вложенный documents) по 10 соединений и отдельные блокировки; S3-клиент собирается дважды; набор сервисов зависит от сочетания `DOCUMENTS_ENABLED` и необязательной конфигурации работ.
- **Задания.** Три независимые настройки BullMQ (diagnostic, `anyko-document-ocr`, `anyko-work-pipeline`) со своими Redis-соединениями, разбором envelope и остановкой; два механизма запусков и outbox (`ProcessingRun/ProcessingOutbox` и `WorkRun/WorkStep/WorkOutbox`). Новый вид задания сейчас означает копию 150–250 строк runtime.

По [направлениям развития](../roadmap.md) сервер получит участников и приглашения, несколько рабочих областей, каталог пакетов, дела, агентский чат, тарифы и квоты, отдельную админку, раздельные worker-пулы и подключения команд. Каждое из этих направлений умножает перечисленные проблемы. Структура закладывается сейчас: часть решений избыточна для MVP, но их цена растёт с каждым новым модулем и маршрутом.

## Решение

### Уровни

| Уровень             | Ответственность                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------ |
| `apps/api`          | HTTP-адаптер: plugins контекста, маршруты по endpoint-описаниям, presenters «модель → контракт»  |
| `apps/worker`       | хост очередей: BullMQ, dispatcher/reconciler, выбор очередей процесса, health                    |
| `backend/runtime`   | единственный composition root `createBackend(config)`; без предметных решений                    |
| `backend/workflows` | процессы, атомарно или последовательно затрагивающие несколько владельцев                        |
| `backend/modules`   | владельцы данных и правил: публичный фасад команд и запросов                                     |
| `backend/profiles`  | содержание профиля БФЛ: поля, правила значений, схемы извлечения                                 |
| `backend/platform`  | технические примитивы: ошибки, scope, транзакции, определения заданий, часы, ID, storage-клиенты |
| `contracts`         | язык HTTP и SSE: схемы, endpoint-описания, каталог кодов ошибок                                  |

Зависимости направлены сверху вниз. `backend` не импортирует `contracts`; модель модуля переводится в контракт presenter'ом API. BullMQ используется только в `apps/worker`; API не ставит задания и обращается к Redis лишь подпиской на временные потоки через порт `platform/realtime` (токены ответа агента). Постоянные события работы остаются в PostgreSQL, поэтому потеря временного потока не теряет данных: после переподключения клиент читает принятый результат из БД. LISTEN/NOTIFY для токенов отвергнут из-за нагрузки на БД и лимита размера сообщения, вызов модели в процессе API — из-за долгих вызовов в HTTP-процессе и отдельных правил отмены и учёта расхода. Правила проверяются dependency-cruiser и архитектурными тестами.

### Модуль: фасад команд и запросов

Модуль предоставляет фасад `createXModule(deps)` с разделёнными `commands` и `queries` и методом `in(tx)`, возвращающим те же команды, привязанные к транзакции. Одна команда или один запрос — один файл в `application/`. Входы и результаты — типы модуля, не DTO. Сценарий, меняющий данные одного владельца, принадлежит модулю; сценарий, атомарно меняющий нескольких владельцев (создание работы с сессией, загрузка с привязкой и outbox), — workflow, вызывающему `module.in(tx)` внутри unit-of-work. Запрос экрана, собирающий несколько модулей, — явный query в workflow с перечнем источников.

Исходный документ адресуется в API через свою работу: `/workspaces/:ws/works/:workId/documents/:docId/source` и `…/images/:index` отдают файл и изображения, `…/result` — результат распознавания той же схемы, что и вне работы; ссылки на изображения в нём ведут на изображения этой работы. `documents` остаётся владельцем файла и результата OCR, а маршруты `/api/documents` первой вертикали удаляются. Распознавание документа вне работы остаётся продуктовой функцией (термин глоссария «Распознавание») и получает свои маршруты `/api/v1/workspaces/:ws/recognitions/...` на том же модуле `documents` и общем механизме `processing` с видом запуска `document.ocr`. Принадлежность документов будущему делу решается вместе со сценарием дела.

`workflows` делится по процессам, а не по агрегату: `work-intake`, `work-analysis`, `work-generation`, `work-view`, `document-ocr`, `document-deletion`. Интерфейс `WorkApi` удаляется.

Состав модулей: существующие `access`, `works`, `documents`, `processing`, `facts`, `templates`, `generation`, `agents` и новый `connections`, выделяемый из `processing`. Подключение модели существует на двух уровнях: платформенное (управляет оператор, расход оплачивает Anyko и учитывает тариф) и подключение рабочей области с ключом команды (управляет owner). В MVP реализовано только подключение области, как сейчас в коде; платформенный уровень появляется вместе с биллингом. Owner явно выбирает подключение области; своё подключение не перекрывает платформенное автоматически. Запуск фиксирует версию подключения, а отзыв выбранного подключения останавливает запуск с явной причиной без перехода на другое: иначе отзыв ключа команды незаметно переложил бы расход на платформу. Прежняя формулировка `data-and-jobs.md` о единственном глобальном подключении оператора заменена. `audit` вводится на этапе 4: команда `record` в транзакции действия, сначала для изменений доступа, подключений модели, удаления и генерации. `cases`, `billing`, `entitlements` появляются со своими сценариями.

### Доверенный scope и права

`WorkspaceScope` — брендированный тип из `platform/scope`; создать его может только `access` после проверки сессии и участия в рабочей области из адреса (`/api/v1/workspaces/:workspaceId/...`, согласовано с [ADR 0008](0008-web-application-architecture.md)). Scope содержит пользователя, область, роль и проверку именованных прав (`works.create`, `connections.manage`). Каждая команда и запрос получают scope первым аргументом; хранилища фильтруют по `scope.workspaceId`. Права проверяет сценарий, маршрут не знает ролей. Роли участия (owner, member) и их права фиксированы в коде; настраиваемые командами роли не планируются, а переход к ним не изменит сценарии, потому что те проверяют права. Оператор платформы — признак пользователя, а не роль в области. Будущий `entitlements` добавляет вторую проверку в том же месте.

Идентификаторы в backend — брендированные типы (`WorkspaceId`, `WorkId`, `DocumentId`) из `platform/ids`; значение получает бренд при разборе на границе (HTTP, задание, чтение из БД). Новые ID — UUIDv7. Типы вводятся постепенно, начиная с сигнатур, меняющихся вместе со scope.

PostgreSQL Row-Level Security откладывается до приёмки готовности к платящим командам: изоляцию сейчас обеспечивают брендированный scope, отсутствие методов хранилища без `workspaceId`, составные ключи и отрицательные тесты. RLS добавится как второй рубеж без изменения сценариев; сейчас его цена — область в каждой транзакции пула Prisma, отдельные роли миграций и заданий, сложная отладка.

Worker получает `ExecutionScope`, восстановленный `processing` из сохранённого запуска, с инициатором для аудита; `access` проверяет, что область не заблокирована. Админка получает отдельный `OperatorScope` без доступа к содержимому работ. Если поддержке понадобится содержимое, это будет отдельный сценарий: owner выдаёт временный доступ, каждое действие пишется в аудит. Сценарий не реализуется до реального запроса поддержки.

### HTTP по endpoint-описаниям

`contracts` описывает каждый endpoint: метод, путь, схемы params/query/body/response, допустимые коды ошибок, вид ответа (JSON, файл, SSE). API регистрирует маршрут из описания через Standard Schema Elysia 1.4, web вызывает то же описание из `lib/api`, OpenAPI строится из него же. Общие функции подключаются plugins: контекст запроса и correlation ID, сессия, scope рабочей области, проверка origin, `Idempotency-Key`, `no-store`, перевод ошибок. Ответы проверяются схемой контракта до измеренной причины отключить это.

Команды, создающие ресурс или начинающие запуск, требуют `Idempotency-Key`. Маршрут через модуль `idempotency` хранит область, команду, ключ, отпечаток входа и итоговый ответ ограниченное время: повтор возвращает сохранённый ответ, тот же ключ с другим входом — `conflict`. Так повтор при плохой сети или двойной клик не становится вторым платным запуском.

Пока web и API выпускаются одним релизом, несовместимое изменение `v1` допускается в одном изменении с web. После появления внешнего потребителя несовместимое изменение получает новую версию маршрутов.

### Ошибки

`platform/errors` задаёт `AppError` с кодом и видом: `invalid`, `unauthenticated`, `forbidden`, `not_found`, `conflict`, `precondition`, `unavailable`. Модуль объявляет свои коды через `defineErrors`; HTTP переводит вид в статус одной таблицей. Каталог кодов, доступных через HTTP, находится в `contracts`; тест сверяет его с кодами модулей. Ответ — `{ error: { code, requestId, fields? } }`: ошибка вида `invalid` может перечислять поля с кодами, чтобы форма показала их у полей; тексты принадлежат web. Ответ сессии содержит участия пользователя и права текущего участия списком именованных строк, а не роль. Ожидаемые ошибки остаются исключениями: Result-тип во всех сценариях не даёт исчерпываемости сверх каталога, но требует переписать весь код.

### Транзакции

`platform/transactions` предоставляет `UnitOfWork.run(tx => ...)` с непрозрачным токеном транзакции; Prisma-тип наружу не выходит. Workflow передаёт токен явно через `module.in(tx)`. Неявная транзакция через AsyncLocalStorage отвергнута как скрытое состояние.

### Фоновые задания

Задание описывается `defineJob`: имя, версия payload, Zod-схема, класс очереди, timeout, политика повтора, обработчик `(ctx, payload)` с `ExecutionScope`, `AbortSignal` и logger. Описание лежит у владельца процесса (`workflows/<process>/jobs.ts`); реестр — явный список в `runtime`. Очереди соответствуют классам нагрузки (`ocr`, `llm`, `render`, `maintenance`), процесс worker выбирает их через `WORKER_QUEUES`, что даёт раздельные пулы на одном образе. Envelope run-заданий (версия, workspace/run/attempt IDs, correlation ID) общий. Scheduled maintenance имеет типизированный системный контекст (clock/logger/signal/correlationId), без workspace и сохранённого запуска; используется внутренний API владельца. Техническая диагностическая очередь остаётся отдельной и работает без БД. Эти два исключения сохраняют глобальное обслуживание и диагностику без фиктивных запусков и миграций (#21).

`processing` становится единым движком запусков: runs, steps, attempts, leases, fencing, outbox и технический расход. Dispatcher и reconciler обобщены по реестру. OCR документа, анализ и генерация работы становятся видами запуска одного механизма и различаются только обработчиками и политикой повтора. Объединение двух существующих наборов таблиц и `DocumentIo/WorkIo` — отдельный этап с миграцией; два механизма рядом отвергнуты, потому что каждый новый вид обработки выбирал бы между ними или создавал третий. Одна очередь с приоритетами отвергнута: долгий OCR задерживал бы короткие вызовы модели.

### Композиция процесса

`createBackend(config)` один раз создаёт пул БД, S3, LLM gateway, часы и генератор ID, собирает модули и workflows и возвращает фасады для HTTP, реестр заданий, health-проверки и упорядоченную остановку. Конфигурация — одна Zod-схема с разделами; необязательные сочетания вида `DOCUMENTS_ENABLED` убираются. Bootstrap приложений только разбирает env и передаёт секции. Correlation ID единообразно проходит путь HTTP → outbox → задание → журнал; OpenTelemetry подключается к `createBackend`, когда появятся несколько экземпляров и сбор трасс.

### Контракты

`contracts` делится по ресурсам (`session`, `works`, `documents`, `catalog`, `connections`, позже `admin`) с subpath-экспортами; корневой `export *` удалён (web #11), админские схемы недоступны пользовательскому web. Пакет описывает форму HTTP и форматную валидацию. Перечень полей профиля БФЛ, их правила и устаревшие ключи переходят в `backend/profiles/bfl`; API отдаёт каталог полей как данные пакета документов, а `contracts` описывает формат каталога. Новый профиль или пакет не требует выпуска web, если использует уже поддерживаемые клиентом типы полей и функции заполнения ([ADR 0012](0012-processing-profiles-and-package-descriptions.md)).

## Отвергнуто

- **NestJS или DI-контейнер.** Второй фреймворк поверх Elysia, декораторы и reflect-metadata; фабрики-функции с узкими зависимостями уже покрывают потребность, а [правила кода](../engineering/code-rules.md) требуют причины для контейнера.
- **Eden Treaty.** Привязывает типы web к реализации API, тянет серверный граф типов в проверку браузерного кода и не даёт независимого от языка контракта для админки, интеграций и OpenAPI.
- **tRPC/oRPC вместо Elysia.** RPC-семантика плохо подходит для загрузки файлов, скачивания и SSE; публичный REST понадобится. Пересматривается, если собственное описание endpoint превысит ~150 строк.
- **Сервис на модуль, CQRS с отдельной БД чтения, event sourcing.** Нет нагрузки и команды, оправдывающих их цену; разделение команд и запросов в фасаде модуля сохраняет путь к ним.
- **OpenAPI из маршрутов Elysia и сгенерированный клиент web.** Шаг генерации в каждом изменении и зависимость web от сгенерированных файлов. Это запасной путь, если собственное описание endpoint разрастётся.
- **Перечень полей БФЛ в `contracts`.** Сохранил бы проверку ключей полей в web при компиляции, но каждое изменение профиля или новый пакет требовали бы выпуска web.
- **Contracts как доменные типы.** Связывает изменения профиля и хранения с HTTP и браузерным бандлом.
- **Generic repository, класс на таблицу, обязательные пустые слои.** Запрещены действующими правилами.

## Последствия

Переход выполняется этапами без изменения поведения, каждый — отдельный PR с обычными проверками и review:

1. Правила: dependency-cruiser для новых границ, `platform/errors`, `platform/ids`, каталог кодов в `contracts`.
2. Композиция: `createBackend`, один пул БД, единая остановка и health, сквозной correlation ID.
3. HTTP-платформа: plugins, endpoint-описания, presenters, `/api/v1`, OpenAPI; совместно с этапом единой загрузки данных web.
4. Scope и права: `WorkspaceScope`, права, область в адресе, общая идемпотентность команд, модуль `audit`; совместно с этапом маршрутов web.
5. Works: сценарии переходят в модули, workflows делятся по процессам, `WorkApi` удаляется.
6. Контракты: subpath-экспорты, `backend` отвязан от `contracts`, профиль БФЛ переходит в `profiles/bfl`.
7. Задания: `defineJob`, очереди по классам нагрузки, BullMQ только в worker.
8. Единый движок `processing` с миграцией таблиц; выделение `connections` — реализовано в #22.

Этапы 1–4 выполняются до новых продуктовых функций, вместе с соответствующими этапами web из ADR 0008; 4 зависит от 3. Этапы 5–8 идут вперемешку с функциями; 5 и 6 независимы, 8 последний. На время перехода сосуществуют два стиля, новое поведение пишется только в целевом. Файлов на сценарий становится больше, а собственное описание endpoint требует сопровождения. Правила, примеры и рецепты добавления — в [backend.md](../engineering/backend.md).
