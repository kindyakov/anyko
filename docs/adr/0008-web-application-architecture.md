# Архитектура web-приложения: уровни, маршруты рабочей области и общий UI-пакет

16 ноября 2026. Уточняет раздел «Web» [ADR 0004](0004-code-organization.md); остальное в нём действует.

Первый вертикальный сценарий собран внутри одного клиентского компонента: все страницы рендерят его с флагами, проверка сессии и оболочка выполняются в браузере, layouts и состояния загрузки/ошибки Next не используются. Feature `works` содержит пять пользовательских сценариев и настройки пространства, серверное состояние загружается тремя разными способами, обработка 401 пробрасывается свойством через все экраны. Для React и Next нет lint-правил, для web нет проверок границ. По [направлениям развития](../roadmap.md) интерфейс получит участников и приглашения, несколько рабочих областей, каталог пакетов, дела, агентскую сессию, тарифы и отдельную админку. Структура закладывается под этот рост сейчас, пока перенос стоит несколько дней.

## Решение

Web остаётся feature-based. Слои FSD не вводятся: их `app`/`pages` конфликтуют с App Router, а нужные свойства дают четыре уровня с направлением зависимостей сверху вниз.

| Уровень     | Ответственность                                                              |
| ----------- | ---------------------------------------------------------------------------- |
| `app/`      | маршруты, layouts, проверка сессии, экраны и координация нескольких features |
| `features/` | пользовательский сценарий: UI, запросы, состояние и правила отображения      |
| `@anyko/ui` | визуальные примитивы, токены и элементы бренда без предметного смысла и HTTP |
| `lib/`      | HTTP-транспорт, query-клиент, ошибки API, server-only сессия и конфигурация  |

Feature предоставляет `index.ts`; чужие features импортируют только его. Зависимости между features образуют граф без циклов. Feature, владеющая данными агрегата (`works`), может использоваться шаговыми features (`fact-review`, `work-generation`), обратное запрещено. Если двум features нужно взаимодействовать, это делает экран в `app/`. Правила проверяются dependency-cruiser и архитектурными тестами, а не только review.

Серверное состояние загружается только через TanStack Query с фабрикой ключей и `queryOptions` в `api/` своей feature. SSE и опрос меняют кэш через инвалидацию, а не через локальные копии данных. Ответ 401 обрабатывается один раз в query-клиенте.

### Клиент API по контрактам

`lib/api` вызывает endpoint-описания из `@anyko/contracts` ([ADR 0009](0009-backend-architecture.md)): путь, параметры, схемы запроса и ответа и допустимые коды ошибок не пишутся в web вручную, и расхождение с API находит `tsc`. Тексты ошибок feature задаёт таблицей по кодам своих endpoint с проверкой полноты (`satisfies Record<Code, string>`); общие технические коды обрабатывает `describeApiError`. Переход выполняется вместе с HTTP-платформой API; до него действует `requestApi` со схемой ответа.

### Рабочая область в адресе

Пользователь может состоять в нескольких рабочих областях, поэтому её идентификатор входит в адрес: `/w/[workspace]/works/...`. Изменение схемы адресов после появления внешних ссылок, закладок и писем-приглашений дороже, чем её введение сейчас. Сегмент содержит непрозрачный ID; читаемый slug может появиться позже с перенаправлением со старых адресов.

Адрес не даёт доступа. API определяет scope из запроса и проверяет участие пользователя на каждой операции; выбор «первого участия» в сессии заменяется явным scope запроса. Web переходит на `/w/[workspace]` сразу, не дожидаясь этого изменения API: маршрут сверяет область адреса с областью сессии, а `/` и прежние `/works/[id]` перенаправляют на новые адреса.

`/` ведёт в последнюю открытую область, которую web запоминает в cookie без секретов; если её нет или участие потеряно — в первую область из списка участий сессии. Переключатель областей находится в оболочке.

Сессия возвращает права пользователя в текущей области. `useCan('works.create')` скрывает или блокирует недоступные действия; решение о доступе принимает API, интерфейс его только отражает.

### Проверка сессии на сервере

`proxy.ts` выполняет оптимистичное перенаправление на `/sign-in` при отсутствии cookie сессии и не обращается к API. `lib/server/session.ts` читает сессию через API с cookie пользователя, кэшируется на запрос через React `cache` и вызывается layout рабочей области и страницами, которым нужны данные пользователя. Layout не считается защитой: при клиентской навигации он не перерисовывается, а права проверяет API. Клиентский компонент больше не решает, показывать ли вход.

### Общий UI-пакет

Примитивы `components/ui`, токены `globals.css` и элементы бренда переносятся в `packages/ui` до появления `apps/admin`: компоненты уже существуют, а [устройство репозитория](../engineering/repository.md) предусматривает пакет вместе с ними. Пакет не зависит от `contracts`, API и features. Примитивы экспортируются из `@anyko/ui`, фоновая графика бренда (WebGL и canvas) — из `@anyko/ui/brand`, чтобы приложение без неё не загружало этот код.

### Формы

Все формы используют TanStack Form 1.x с закреплённой версией; две техники для одной задачи не допускаются. Библиотека принимает Zod-схемы из `contracts` через Standard Schema без адаптеров, работает с управляемыми полями Base UI без обёртки на каждое поле и подписывает компоненты на отдельные поля, что важно для большой формы сведений. Связка с Base UI Field (значение, изменённость, ошибка, фокус на первом ошибочном поле) создаётся через `createFormHook` в `@anyko/ui/form`, библиотека — peer-зависимость пакета. Features не импортируют библиотеку напрямую, поэтому переход на следующую major-версию затрагивает одно место.

Перенос несохранённых правок на новую серверную редакцию — чистая функция `fact-review/model`, а не возможность библиотеки: поле, не изменённое пользователем, получает новое серверное значение; изменённое пользователем сохраняет правку; изменённое обеими сторонами показывается как конфликт. Результат загружается в форму через `reset`. Функция проверяется unit-тестами без React и не зависит от версии библиотеки.

Несохранённый черновик хранится только в памяти формы: формы содержат персональные данные клиента, а browser storage оставляет их на устройстве. При уходе со страницы с несохранёнными правками интерфейс предупреждает пользователя.

Ошибка вида `invalid` в контракте может содержать список `fields: { path, code }[]`. Форма показывает такие ошибки у соответствующих полей; тексты берутся из таблицы кодов feature.

### Разделы

Подключения моделей переходят из модального окна оболочки на страницу `settings/connections` (feature `connections`, право `connections.manage`); раздел `settings/` примет участников, тарифы и профиль области. Раздел распознавания документов вне работы называется `recognition` (feature `document-recognition`), чтобы не совпадать с серверным модулем `documents`, владеющим исходниками. Документ работы адресуется через свою работу, а раздел распознавания использует собственные endpoint `/workspaces/:workspaceId/recognitions/...` на общем механизме обработки.

## Отвергнуто

- **FSD.** Шесть слоёв и сегменты дробят небольшие сценарии на множество файлов; слой `entities` заменяется feature-владельцем данных с публичным интерфейсом.
- **Рабочая область только в сессии.** Переключение области меняет данные под теми же адресами и ломает ссылки между пользователями разных областей.
- **Проверка сессии в клиентском компоненте.** Даёт мигание экрана, не перенаправляет вложенные маршруты и смешивает решение о доступе с отображением.
- **Server Actions и Route Handlers для предметных операций.** Повторяют правила API; Route Handler остаётся прозрачным транспортом.
- **Адрес рабочей области после изменения API.** Маршруты пришлось бы переносить дважды.
- **React Hook Form.** Каждое управляемое поле Base UI требует `Controller`, Zod 4 подключается через адаптер, `watch` несовместим с React Compiler; сохранение изменённых полей при `reset` в ноябре 2026 ещё исправлялось для массивов. Следующая major-версия ломает API так же, как у TanStack Form.
- **Перенос правок средствами библиотеки.** У TanStack Form 1.x его нет, у React Hook Form он нестабилен для таблиц; предметное правило конфликта не должно зависеть от библиотеки.
- **Черновик формы в localStorage/sessionStorage.** Оставляет персональные данные клиента на устройстве после выхода.

## Последствия

Переход выполняется этапами без изменения поведения: правила и проверки, платформенный слой, маршруты, разделение features, единая загрузка данных, UI-пакет, E2E. Каждый этап проходит обычные проверки и review. Правила написания кода и рецепты добавления находятся в [web.md](../engineering/web.md).
