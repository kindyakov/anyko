# Профили обработки и описания пакетов

21 ноября 2026. Уточняет [ADR 0006](0006-document-packages.md) и [ADR 0009](0009-backend-architecture.md). Принципы происхождения сведений из [ADR 0011](0011-work-agent-proposals-and-template-format.md) не меняются.

## Контекст

Сейчас в Anyko один профиль: банкротство физического лица. Новые работы создаются по пакету `bfl-bankruptcy-v12`. В MVP не планируются ни новые пакеты, ни админка. Примерно через год оператор платформы должен добавлять пакеты из других областей, например иск о взыскании долга, без переписывания и дублирования кода. В коде профиль пока не выделен:

- общие модули сведений, агента, шаблонов и генерации напрямую импортируют `profiles/bfl`;
- ключи всех полей собраны в одном перечне, а сведение и подтверждение перебирают его целиком;
- в общих промптах есть указания, специфичные для банкротства, а инструмент поиска арбитражного суда включается по наличию полей суда;
- поведение шаблона выбирается сравнением строки версии;
- предпросмотр в web отдельно повторяет подготовку данных для DOCX;
- состав пакета распределён между кодом, `package.json` и SQL-миграциями;
- ключ кэша извлечения не учитывает инструкции и набор полей.

## Решение

**Профиль — модуль кода с версией.** Runtime регистрирует профиль по идентификатору и ревизии. Профиль включает:

- поля;
- правила проверки и сведения;
- предметные указания агенту для каждой стадии;
- разрешённые инструменты с проверкой происхождения их результатов;
- функции заполнения.

Версия пакета указывает профиль. Работа или задание один раз разрешает зафиксированную версию пакета в профиль и набор полей пакета. Модуль сведений получает только поля пакета и правила сведения. Агент получает политики стадий и разрешённые инструменты. Общие модули не импортируют профили и не передают реестр профилей друг другу.

**Ключи полей остаются плоскими и устойчивыми.** Общее ядро сведений состоит из типов значений: ИНН, СНИЛС, паспорт, адрес, дата, деньги. Тип задаёт формат записи и проверку. Поле состоит из ключа, типа значения, роли и подписи. Формат значения, допустимое доказательство и обязательность поля задаются отдельно. Например, `plaintiffInn` и `defendantInn` имеют один тип и подтверждаются независимо. Подпись можно сменить без переименования сохранённого ключа. При публикации пакета ключ, совпадающий с ключом другого источника, считается ошибкой. Модель участника вводится, когда понадобятся несколько участников в одной роли, например два ответчика.

**Описание пакета — проверяемое значение в коде.** На каждую версию пакета приходится одно описание:

- версии шаблонов;
- поля;
- требования к исходным документам;
- приложения;
- тексты указаний;
- ссылки на функции заполнения профиля с типизированными параметрами.

При публикации проверяются теги DOCX, повторяющиеся строки таблиц, типы значений и контрольная сумма. Опубликованная версия неизменяема. Повторная публикация с тем же хэшем безопасна, другой хэш под тем же номером является ошибкой. Будущая админка оператора публикует через ту же проверку. Конструктора выражений нет:

- готовый текст и согласованные варианты — данные описания;
- склонение, выбор абзаца по сведениям и расчёт пошлины — функции заполнения с версией и тестами.

Текст описания не даёт агенту полномочий: инструменты разрешает только код профиля.

**Одна чистая функция заполнения бланка.** На вход она получает версию бланка, значения и явный контекст и возвращает значения мест шаблона. Web вызывает её на черновике юриста, чтобы предпросмотр менялся сразу при вводе. Сервер вызывает её на сохранённой редакции сведений при генерации. Пакет из типов полей и функций заполнения, которые уже поддерживает клиент, публикуется без выпуска web. Новая функция заполнения выходит вместе с выпуском web до публикации пакета, который её использует. Новый серверный инструмент агента выпуска web не требует. Это уточняет утверждение ADR 0009 о том, что новый пакет не требует выпуска web.

**Ревизия каждой стадии в ключе кэша.** Идентичность исходника отделена от ревизии стадии. Ревизия извлечения складывается из фактических результатов чтения изображений, определений полей с указаниями, схемы результата и правил извлечения. Изменение только DOCX модель не вызывает. Запись кэша без ревизии считается промахом.

**Старые версии пакета удаляются чистой миграцией.** Пользовательских данных на версиях до v12 нет: все работы локальные и тестовые. Миграция удаляет версии пакета v1–v11, их бланки, плейсхолдеры, требования, а также работы, задания, генерации и файлы по ним. Затем удаляются исполняемый код и ветки этих версий. Режим только для чтения и перевод работ на новую версию не нужны. Когда появятся реальные пользователи, выбор между архивом и переходом нужно будет принять заново, отдельным решением.

**Шов проверяется вторым профилем.** Тестовый мини-профиль «иск о взыскании долга» имеет два пакета с разными наборами полей. ИНН используется в двух ролях, присутствуют оба поля суда (`courtName` и `courtAddress`), арбитражный инструмент не разрешён. Профиль проходит штатный выбор пакета, сведение, подтверждение и реальный DOCX. В пользовательский каталог он не попадает.

## Отвергнуто

- **Пространства имён ключей `core.*` и `bfl.*`.** Пришлось бы переносить сохранённые сведения, а конфликты ключей и так ловит проверка при публикации пакета.
- **Предпросмотр на сервере при каждом вводе.** Оправданной задержки и требования офлайн-режима нет. Чистая общая функция даёт тот же результат без обращения к серверу.
- **Конструктор формул для оператора.** Он избыточен на горизонте года: новое поведение всё равно требует тестов и проверки юриста.
- **Описание пакета в отдельном JSON-файле уже сейчас.** Сериализуемое значение в TS с проверкой во время выполнения даёт ту же форму данных и остаётся типизированным.
- **Архивный режим для старых версий.** Сейчас он защищал бы только тестовые данные, а стоил бы снимка каталога и отдельных сценариев чтения.

## Последствия

Порядок работ:

1. Исправить кэш.
2. Зафиксировать результат v12 эталонными примерами трёх DOCX.
3. Удалить версии v1–v11 чистой миграцией вместе с их кодом.
4. Написать тестовый второй профиль.
5. Выделить шов профиля, набор полей пакета, типы значений и разрешения инструментов. Перенести указания по банкротству из общих промптов.
6. Перевести заполнение DOCX и предпросмотра на одну функцию, а v12 — на описание пакета. Убрать проверки по строкам версий.

Сохранённые SQL-миграции каталога остаются историей развёртывания.
