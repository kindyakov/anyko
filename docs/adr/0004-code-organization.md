# Feature-based web и модульный backend с ports/adapters

5 ноября 2026. Пользователь выбрал feature-based для web и предметные модули
с портами/адаптерами для backend. Решение дополняет модульный монолит из ADR 0001.

## Web

Next App Router отвечает за маршруты, layouts и framework loading/error states.
Пользовательский сценарий принадлежит `src/features/<name>`: UI, состояние и
предметные HTTP-вызовы находятся рядом. Feature предоставляет небольшой явный
интерфейс. Маршрут компонует features; прямые циклические связи и импорт чужих
private-файлов запрещены. Совместное поведение координируется на уровне экрана.
Подпапки ui/model/api появляются по необходимости. Стандартные слои FSD не вводятся.

Технический HTTP-клиент находится в `lib/api`, серверная конфигурация — в
`lib/server`. Server-only код не импортируется клиентскими компонентами.
HTTP DTO принадлежат browser-safe `contracts`. Next Route Handlers допустимы
для прозрачного транспорта к API, без повторной реализации предметных правил.

## API и worker

API является HTTP-адаптером: разбирает запрос, проверяет сессию/участие,
получает доверенный scope, вызывает серверную операцию и отображает результат.
Worker является адаптером очереди: валидирует envelope, сверяет каноническое
состояние операции и вызывает серверный сценарий. Elysia Context и BullMQ Job
не входят в интерфейс предметного сценария.

## Backend

Верхний уровень `modules` разделён по владельцам поведения и данных. Внутри
модуля изменения группируются по вертикальным сценариям. Чистые domain rules
выделяются при появлении инвариантов; application описывает команды/запросы и
нужные им порты. Infrastructure реализует persistence, storage и MinerU.
Сценарий зависит от узкого порта, а не от Prisma, S3 SDK или HTTP-протокола OCR.

`workflows` координирует публичные интерфейсы нескольких модулей. `runtime`
собирает реализации и владеет ресурсами; в нём нет предметных решений.
Класс/repository/mapper на каждую таблицу и пустые архитектурные слои не нужны.
Порты отражают конкретные операции, а не универсальный CRUD над любыми данными.

## Последствия

Загрузка и OCR проверяются как один сценарий через настоящие адаптеры.
Подмена MinerU на тестовый HTTP-сервис проверяет протокол и ошибки, но не
считается проверкой реального OCR. Инварианты транзакций, scope и принятия
результата проверяются на PostgreSQL. Правила владения, outbox и удаления
из `data-and-jobs.md` остаются обязательными.

Первая вертикаль: закрытый доступ → загрузка PDF → source artifact → сохранённый
run/outbox → worker → MinerU → immutable result → статус и чтение результата.
